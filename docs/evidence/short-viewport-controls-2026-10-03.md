# Short-screen controls and RTL centering — 2026-10-03

Short, narrow landscape views could shrink the whole solo surface enough to make keyboard keys smaller than 32 pixels. The existing compact board rule applied only in portrait orientation. At 500×494 the controlled baseline measured keys of about 31.5 pixels without the save notice and 27.9 pixels with it. The race surface measured about 28.1 pixels at that size and 27.2 pixels at 844×390.

The extended horizontal-geometry checks also exposed a separate Arabic failure: expanding the relatively positioned solo fitting wrapper could move much of the game outside the left edge. Earlier save-notice checks verified vertical keyboard visibility but did not check both horizontal keyboard edges. The new check includes horizontal bounds of the clue, answer board, keyboard, actions and navigation.

The solo wrapper now uses an absolute physical anchor before the existing fitting transform. Its children retain locale direction. The compact clue/board rule applies to short narrow views in either orientation. The race surface caps board size before scaling at short narrow widths, and uses a two-column puzzle/keyboard layout on landscape screens at least 600 pixels wide and no more than 600 pixels tall. Existing scoreboard text, answer controls, penalties and actions remain visible. No copy or locale key changed, and no gameplay, authority, persistence or SDK request changed.

## Remaining Firefox fitting case

Loading a game in a desktop-sized Firefox window and then resizing it to the short viewport can still leave the solo scale too small: the recorded German unsaved view has keys around 25.3 pixels. A fresh load at that same measured viewport gives approximately 33.6 pixels. Clearing the transform during measurement and substituting offset height for scroll height did not fix that transition in targeted probes, so neither change entered production. Font/layout timing is a candidate rather than a proven cause. The raw records retain the failed transition and probes alongside the passing fresh-load cases.

Firefox MCP reports window dimensions that include browser chrome and clamps very narrow requests to 500 pixels. Assertions use measured inner dimensions; the 280-pixel cases are verified in Chromium. This pass does not claim a 32-pixel Firefox minimum across resize transitions, a universal touch-size guarantee, or a production latency improvement.

The diagnosing-bugs skill guided the measured baseline, isolated probes and final regression checks. The broader goal remains active. The unresolved Firefox transition, long-content stress cases, and recovery ownership for Facebook/Reddit persistence remain candidates for subsequent work.
