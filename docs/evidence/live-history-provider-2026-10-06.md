# Live Activity history ownership — 6 October 2026

Activity now removes an old provider's history rows and actions during the replacement commit. A late old projection cannot supply the replacement panel's state, and an old Rematch control cannot create a journey through the new provider. Ordinary profile and callback updates preserve the loaded row and add no history request.

The actual `RaceTournamentEntry` → Activity → `RaceContextBoard` → `LiveRaceHistory` → Rematch path reproduced the defect. A native fixture control replaces the provider. The parent layout observes one old row and activates its native Rematch button before passive cleanup; the real coordinator then calls the new provider's rematch method with the old history ticket. The original minimal probe fails two of 12 checks in both React modes, with a stable-parent-update control passing. It still reproduces against the preserved original source after the fix, while the same probe against the final source passes all 24 checks across both modes.

`LiveRaceHistory` now owns a keyed panel selected by provider identity, its history callback, and locale. Conditional React state alignment replaces that panel before it commits old rows under a new provider. Using React state retains the committed key when a prepared replacement suspends and is abandoned. The panel keeps existing validation, eight-second read bounds, generic translated loading/retry copy, server-authoritative block/report behavior, and explicit rematch selection. The public props remain compatible.

Each deferred read captures its original callback and checks that its effect still owns admission before calling the provider. This prevents a retired Strict Mode setup from issuing a redundant read and prevents a queued read from borrowing a subsequently replaced callback. The old development baseline admits two initial reads; the fixed browser matrix admits exactly one in every case. This is a local request-count improvement, not a production network latency benchmark.
