# Single-player startup recovery coalescing — 5 October 2026

Automatic single-player recovery now has one observer for an in-flight question load. That observer resynchronizes the host and counts the result once. Reconnect and foreground signals still reset failure history, but they do not schedule empty callbacks while that recovery is active. Once it settles, the existing bounded backoff or immediate reconnect path can admit the next attempt.

Previously, provider reads were deduplicated while recovery callers were not. Twenty reconnect signals produced 21 observers awaiting one read. When it failed, each observer incremented the failure count and replaced the timer, leaving a 30,000 ms retry instead of the first 1,000 ms retry. A single reconnect signal could also double-count the failure. The new guard belongs to the current account/locale effect and clears in `finally`, so completion or retirement cannot leave a later attempt locked.

The minimal unit regression failed because only one provider call had occurred after the first backoff, when two were expected. The corrected full `PlayHostApp` fixture failed three of seven assertions: 21 observers, no timely retry, and no playable question. A separate observer-only probe restored recovery but exposed 20 empty zero-delay timer callbacks. Suppressing those callbacks completed the change. The matching expanded baseline failed 42 of 107 assertions. Its recorded native timer retained the 30-second delay; this is a requested client backoff, not measured internet latency.

The final real React fixture covers ten scenarios in three viewports, in both development and production: online, foreground, mixed signals, hidden, single signal, successful held read, retirement, offline, consecutive failures and reconnect during idle backoff. Each mode passed 321 assertions. Native answer input worked after recovery, genuine failures retained the 1,000/2,000 ms progression, and retirement stopped retries. Existing question-ordering and Classic preparation checks added 1,410 assertions, for 2,052 passing browser assertions.

Firefox verified one held recovery through 20 reconnect signals, a fresh read 1,001 ms after failure, native `P` input, foreground recovery and consecutive real failures. All five verified records have no browser errors or unhandled rejections. The first exploratory Firefox control outlived the read deadline and is preserved separately, excluded from verified evidence. In the final foreground and failure-chain records, nested callback arrays show the complete timeline; the held read and observer counts were copied before failure.

The first full-host prototype also put its test controls behind the loading overlay, so its native clicks waited for the original 15-second deadline. Those records are explicitly marked `pre-overlay-control` and are not the bug proof. Corrected fixture controls sit above the overlay solely to inject lifecycle signals during the held read. Product controls and admission rules were not changed.

Validation passed: 2,856 unit tests across 300 suites, types, 25,528 documented declarations across 1,144 files, all six isolated target audits, and eight built-artifact browser tests across three suites. The buffered transition threshold remains 100 ms. YouTube used the incomplete-content fixture build, not release certification. No product text, provider SDK, progression, economy or reward contract changed.
