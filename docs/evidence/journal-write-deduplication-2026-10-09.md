# Failure-safe journal write deduplication, 9 October 2026

Single-player pending-play recovery avoids an identical synchronous journal write after Continue admission. The draft effect first compares its small cell array and cursor with the current journal segment. Only when those fields appear unchanged does the concrete storage writer read the same key and compare the complete serialized payload. Matching durable bytes already contain the exact request and draft, so no second setItem is needed. Changed letters/cursor use the existing unconditional write path; request admission and other explicit writes also remain unconditional.

There is no in-memory persistence cache. Deleted or replaced durable bytes are rewritten. A failed draft write remains retryable even though its in-memory object already changed. If the optional read throws, the writer still attempts its original setItem path. The comparison includes every serialized field, not just letters, so a changed request, queue, account scope or buffered segment cannot be acknowledged as an old checkpoint. No saved protocol field, server authority rule or visible text changed.

Three new behavioral unit cases verify matching persisted data when subsequent writes are restricted; rewriting an externally removed checkpoint and retrying a changed draft after failure; and a usable writer with a restricted reader.
