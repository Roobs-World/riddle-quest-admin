# Exclusive opponent search intent

Two real Firestore emulator reproductions failed before the fix: an initially empty lookup issued a bot fallback, then a newly published human recording caused retry of the same request to return a human offer. This also occurred after the fallback was accepted, bypassing consumed-intent recovery and creating a second offer kind under one search identity.

Discovery now batches the recorded and fallback receipt reads in one ingress RPC. A valid fallback is replayed without rescanning a changing human pool; an accepted fallback reports intent-consumed, an expired fallback reports intent-expired/new-intent, and conflicting stored receipt kinds fail closed as data-loss. Recorded offer commit reads the competing fallback receipt and replays a concurrent fallback winner instead of writing a human receipt. Fallback creation uses a Firestore transaction reading both receipt kinds before create; a recorded winner prevents fallback issuance. An existing recorded selection that becomes ineligible cannot silently switch to fallback under the same intent.

The first focus run exposed a test fixture coupled to the old single-reference get method. Its deadline injection now follows the real two-document ingress batch and asserts no history/configuration work after the batch consumes the deadline. Production checks the work deadline before either replay path. Extra ingress and committing document reads, including fallback issuance transactions, are included in the existing lookup meter. The ingress adds one physical document read, batched with the original receipt; recorded commit adds one competing receipt read. The fixed document/transaction/deadline budgets remain enforced.

The first full backend run passed 1,004 tests and exposed one architecture fixture expecting the old two-document commit batch. Its assertion now requires the recorded receipt, challenge and competing fallback receipt in the same SDK batch, preserving the batching invariant.

The focused fallback and recorded matchmaking suites passed 55 tests. New cases cover unaccepted and accepted fallback replay after human publication, a fallback winning after a stale recorded ingress read, a recorded winner preventing fallback creation, and expired fallback recovery with a healthy human pool. Original identity, expiry, concurrent acceptance and full gameplay cases remain covered. Browser compatibility uses the existing injected desktop/mobile discovery harness; server mutual exclusion is evidenced by actual emulator transactions.

No UI text or locales change. The completion task runs full backend coverage, client/core checks, all seven isolated builds and dependency/security gates before recording current-source completion. Jest activation is authorized; publication and review remain held. Firebase Functions deployment is authorized, but this verification performs no external deployment. The ongoing reliability audit remains active.
