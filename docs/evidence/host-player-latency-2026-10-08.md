# Built player-path latency assessment

No reliable wall-clock latency improvement is established for the preceding 9,879-byte startup reduction. Five alternating cold browser contexts per side, per engine, produced overlapping timing ranges. These are actual compiled Jest artifacts with the deterministic trusted provider harness and an unthrottled local server, not live production backend latency.

Reported runs exclude the diagnostic long-task observer. Current first-riddle delivery medians are 90.3 ms in Chromium (87.2–109.7 ms) and 88 ms in Firefox (83–104 ms), compared with 93.5 ms (88.8–107.1) and 89 ms (82–194) respectively. Current Submit-feedback medians are 12.8 ms in Chromium (12.3–13.4) and 9 ms in Firefox (8–11), compared with 12.6 ms (12.3–12.8) and 10 ms (9–11). Exploratory exact two-sided rank-sum permutation comparisons do not establish a difference: first-riddle p=0.548/0.810 and feedback p=0.373/0.571 for Chromium/Firefox. These small fixture samples do not prove timing equivalence or exclude benefits on other devices/networks.

The original and current production source/build identities are verified from the preceding completed passes. Twenty diagnostic and twenty unprofiled built-game journeys run actual onboarding, load an issued Classic riddle, submit CRANE against the piano fixture, withhold the authority reply, observe actual colored cells, type the next P draft, then release confirmation. Every run checks the actual guess request/receipt, corrected feedback and surviving draft. There are no browser errors, unhandled rejections or unapproved external requests. Timings run inside the actual browser handler rather than timing Playwright automation. Onboarding user-action delays are outside the feedback interval; first-riddle delivery is measured from navigation start before those delays.

The diagnostic Chromium runs contain no observed >50 ms long tasks. The observed local client paths spend roughly 16–30 ms from ready signal to issued-riddle delivery and around one frame on feedback. The 250 ms recovery fallback is not the normal startup critical path in these traces; the game-ready bridge initiates loading sooner. This evidence does not justify shortening recovery cadence or changing gameplay rendering based solely on these desktop results. Real provider/network delays, lower-end devices and multiplayer transport remain distinct assessment scopes.

Evidence lives under `artifacts/host-player-latency-2026-10-08/`: measurement plan, two harnesses and their hashes, forty complete event/resource traces, browser versions, summaries and exploratory rank comparisons, exact previous/current artifact hashes, unchanged selected-source manifests and verifier. Both native engine runs settle with exit code zero and their servers/contexts close in finally blocks. No production code changes are made in this assessment. Current six-target/client checks are reused only after verifying that all 2,481 selected inputs match the last completed source snapshot; no historical backend authority certification is inferred.

The game improvement goal remains active. The next investigation is multiplayer transport and current backend reliability, where the synthetic single-player measurements provide no performance or correctness certification.
