### Facebook Instant Games platform data

The Facebook target loads SDK v8 only in its own artifact. It reads the game-scoped player ID, requests signed player information bound to a one-use game nonce, uses asynchronous FBInstant player data for preferences/resume state, reports loading progress, calls `startGameAsync`, and flushes on pause. The signed assertion and raw game-scoped ID cross into the Firebase identity endpoint; Meta name/photo APIs are not read by the current implementation.

The server stores the raw game-scoped ID only in server-readable `providerIdentities`. It derives a generation-separated `facebook_<40 hex>` Firebase UID with a dedicated HMAC secret and issues custom claims containing only the provider and account generation. One-use nonce records store creation/expiry/consumption and, after consumption, a SHA-256 player-ID hash. New nonce issuance now includes a Firestore timestamp at its exact five-minute numeric acceptance deadline. The committed `facebookIdentityNonces.expiresAt` policy and bounded legacy backfill prepare asynchronous physical cleanup; the exact live field read on 2026-10-01 showed no TTL configuration, so deployment and physical deletion acceptance remain outstanding. Expired, missing, consumed or corrupt nonce records cannot authenticate. Provider identity records remain without TTL. Firestore rules deny all client access to provider identities and nonce records. See [nonce retention evidence](evidence/facebook-nonce-retention-2026-10-01.md).

In-game deletion and Meta's signed deletion callback converge on the same cleanup. The provider record advances its account generation, clears the active UID, and retains the server-only provider scope—including the raw game-scoped player ID and app ID—plus status/generation, creation metadata, a SHA-256 old-UID hash, and deletion metadata. The raw player ID is required to derive a later generation-separated UID; a later explicit fresh start creates that UID and a 300-coin profile. The callback receipt uses an opaque confirmation code and exposes no player identifier. Before in-game deletion, a random browser deletion epoch invalidates other current-build same-origin tabs and an origin-wide Web Lock drains accepted work; after server success, the two exact FBInstant preference/player-state keys are nulled and flushed. The epoch contains no player identifier and remains only as a same-origin coordination generation. Live Meta retention, cross-device SDK propagation, platform deletion behavior, contract roles, age-category availability, and real-device behavior remain production-verification and owner/counsel items.

Facebook social context IDs are never stored raw by game services. The server stores a domain-separated SHA-256 context key, context type, locale, provider-scoped member UIDs, join/active state, host UID, and seven-day logical expiry. Independently authenticated joins establish server-owned known-rival relationships; the client cannot nominate another player. A context-board entry contains the provider-scoped UID, authoritative run ID, adjusted milliseconds, completion time, and the same seven-day expiry, but callable responses project only rank/time/current-player. The committed TTL covers entry documents. The new bounded hourly Facebook scheduler atomically removes expired parents and their score entries, retaining only identity-free metadata within its original 30-day history window. A read-only Functions check on 2026-10-01 confirmed that scheduler is not deployed, so automatic physical cleanup remains a rollout gate. Parent TTL stays absent because it does not cascade to scores. Rollover deletes every old entry and retains identity-free board metadata for 30 days. Account deletion removes the UID and entry from memberships and deletes all remaining entries before an empty board. No Meta name or photo is copied into these records.

Native Facebook tournament creation/sharing sends Meta an official best adjusted time in milliseconds, a localized title and generated identity-free PNG, and a five-field payload containing a versioned kind, locale, official daily ID and UTC start/end timestamps. An improved authoritative run may update the matching native score. The game reads the native tournament/context ID, expiry and payload only in memory to verify presentation scope; it persists no raw native tournament ID and sends no Firebase UID, run ID, answer or reward in this payload. Meta already associates its authenticated player with native participation; this does not make the transfer anonymous to Meta. Meta retention, recipient copies, deletion and hosted device behavior remain unverified. Native data never supplies official ranks or economy authority. See [adapter and browser evidence](evidence/facebook-native-tournaments-2026-10-01.md).

Presence is explicitly opt-in. RTDB stores one random session record per active tab/device with provider target, coarse `online`/`playing`/`racing` state, and server timestamp, plus a server aggregate and opt-in bit. Server-only visibility and reverse-index edges restrict reads to established rivals; either party's block and account deletion revoke them. `onDisconnect` removes crashed connections. When the final connection disappears, aggregation persists an unreadable `offline` status and `presenceOptIn: false`; account deletion removes those records. Session IDs are not Meta IDs and are not exposed through rival reads.

### Reddit Devvit platform data

The Reddit webview does not receive raw Reddit identity or call Firebase directly. The
request-scoped Devvit server compares the current-user profile ID with trusted
`context.userId`, accepts only bounded profile fields and HTTPS avatars from the
approved Reddit CDN allowlist, and signs an operation-specific assertion to Firebase.
Firebase stores the raw Reddit ID and a sanitized profile cache with a 24-hour
logical expiry only in a server-readable provider record. Expired profile fields
are suppressed from social responses. A bounded hourly field-removal scheduler is
now prepared locally but is absent from the deployed-function listing; physical
cleanup requires index readiness, deployment and production verification. Refresh
and account deletion already remove the cache. A TTL on that nested field would
delete the identity record itself and must not be used. It derives a generation-separated
`reddit_<40 hex>` UID with a dedicated HMAC secret; browser responses contain opaque
session state, not the raw ID, name, or avatar.

Reddit preference/player storage is asynchronous and authoritative in Firebase. Local
browser state remains low-integrity. In-game deletion advances the provider account
generation before cleanup and deletes the cached profile; an explicit fresh start
creates the next generation with 300 coins. Stale generation retries cannot delete the
new account. Devvit Redis is not used as canonical global profile, balance, receipt, or
entitlement storage. The inactive-by-default Reddit commerce path stores server-only
Gold order replay receipts, refund receipts, and hidden coin debt in Firebase; it is
not exposed until Reddit approves the products and the deployment explicitly enables
commerce. Checkout metadata contains a stable 256-bit HMAC account tag derived by the
Devvit server from app scope and Reddit user ID. It contains neither the raw ID nor a
Firebase UID and is used to manually isolate bounded order-history recovery before each
order re-enters the idempotent Firebase ledger. Notifications are not complete and must
not be described as active processing.

The prepared Devvit server also retains one installation-local canonical game-post
reference in Redis. Its value is a `t3_` post ID or a constant pending-creation marker;
it contains no player profile, identity or economic data. Pending creation has no
automatic expiry because an uncertain submission must not authorize a duplicate.
An unavailable retained post does not trigger replacement. Installation retention
and operator recovery still need hosted verification; see the
[canonical post runbook](reddit-games-operations.md#canonical-game-post-creation).

The inactive-by-default Reddit referral ledger stores only hashed seven-day tokens,
provider-scoped Firebase UIDs in unresolved bindings/daily caps, and idempotent settlement
receipts. Referral provenance stores locale, sandbox/production environment, and a
domain-separated hash of the signed Reddit post ID—not the raw post ID. Account deletion removes live tokens, bindings, and caps and replaces linked
settlements with identity-free replay tombstones. Reddit post-entry attribution is not
active until a real Devvit post payload is captured and its server trust contract passes.

### 2. Riddle Quest Firebase/GCP data

#### Identity, authentication, and profile

- For a Jest identity that has not been deleted, each session, including a platform guest, exchanges a recent signed Jest assertion for a Firebase custom token. The Firebase UID is a stable pseudonymous value derived from the Jest player ID. The custom token contains the raw `jestPlayerId` and registration flag as claims ([exchange endpoint](../firebase-functions/src/jest/jestEndpoints.ts), [browser sign-in](../packages/portal/src/jest/JestPlayApp.tsx)).
- Game-account deletion first writes `jestAccountDeletionTombstones/{uid}` under the authenticated Firebase UID with exactly `schemaVersion: 1`, `recreationBlocked: true`, and a server `deletedAt` timestamp. The record's stable document ID and deletion time remain pseudonymous, linkable data. Every current authenticated non-delete callable checks this guard, including for a historical non-deterministic Firebase UID. For a current deterministic Jest UID, it also blocks normal identity exchange before any Firebase custom token is minted and prevents purchase, subscription, and referral-grant flows from recreating or crediting the deleted identity ([deletion guard](../firebase-functions/src/jest/jestAccountDeletion.ts), [callable wrapper](../firebase-functions/src/shared/sentryHandlers.ts), [guarded endpoints](../firebase-functions/src/jest/jestEndpoints.ts), [guarded referral grants](../firebase-functions/src/jest/jestReferralGrant.ts)).
- Deletion also permanently occupies that deterministic UID with a disabled Firebase Auth sentinel before waiting for older operations to drain. It replaces the email with the non-deliverable pseudonymous `deleted-{uid}@players.jest.invalid` value; clears display name, phone, photo, linked providers, multi-factor enrollments, and custom claims; and revokes refresh tokens. If the Auth record is missing, deletion creates the disabled record and handles a concurrent token-redemption create race. Identity exchange also rechecks the Firestore guard after token minting. Together, the retained disabled record and guard prevent a custom token minted just before deletion from recreating an enabled identity ([Auth sentinel](../firebase-functions/src/jest/jestDeletedAuthUser.ts), [post-mint check](../firebase-functions/src/jest/jestEndpoints.ts)).
- The authenticated deletion callable accepts a deterministic Jest UID only when the trusted `jestPlayerId` custom claim is present and derives back to that same UID. This prevents an old or inconsistent token from silently skipping referral cleanup or targeting one Firebase UID while supplying another platform identity. A stale claimless token must refresh through the normal signed Jest session, while the dedicated deletion-retry endpoint derives its subject from a fresh signed Jest assertion ([callable binding](../firebase-functions/src/profile/accountDeletion/deleteAccountCallable.ts), [signed retry endpoint](../firebase-functions/src/jest/jestEndpoints.ts)).
- Every authenticated Firebase callable, regardless of UID format or custom claims, transactionally verifies that the deletion guard is absent and creates an `activeOperations` child lease before running. The deletion callable alone skips its own lease. A lease stores only `expiresAt`, which is an expected callable deadline plus a 30-second diagnostic margin, and is normally deleted immediately afterward. That timestamp is not treated as proof that a timed-out Cloud Run execution stopped: deletion writes the permanent guard first and returns a retryable result while *any* lease remains, including one past its deadline or malformed. An orphan lease requires explicit operator reconciliation only after proving the old execution/revision can no longer write ([callable wrapper](../firebase-functions/src/shared/sentryHandlers.ts), [lease protocol](../firebase-functions/src/jest/jestAccountDeletion.ts), [callable timeout](../firebase-functions/src/shared/callableSecurity.ts)).
- A new Firestore `users/{uid}` profile receives the UID, a **synthetic** `${uid}@players.jest.invalid` address (not a player email), a Jest-ID-derived default username, coin/entitlement flags, timestamps, preferred language, statistics, progress, and achievements ([Jest user creation](../firebase-functions/src/jest/jestUser.ts#L5-L23)).
- The supported user schema also includes username/display name, optional avatar URL, language, currency, registration/login/daily dates and keys, detailed play statistics, progression, achievements, purchase flag, and legacy/unused notification fields ([user schema](../packages/core/src/validation/firestoreSchemas.ts#L89-L137)).
- Usernames are normalized and reserved in server-only `usernameReservations`, which stores the Firebase UID, normalized and display username, reservation hash, and update time ([reservation code](../firebase-functions/src/profile/usernameReservations.ts#L6-L64)).
- Firebase Auth persistence is not explicitly configured; the client calls `getAuth` and signs in with a custom token. The effective browser persistence, token lifetime, and provider-side auth logs must be verified against the deployed Firebase configuration ([Firebase client](../packages/portal/src/firebase.ts#L103-L108)).

Firestore rules let an authenticated player read only their own `users/{uid}` document; writes are server-only. Direct leaderboard reads and writes are denied; the authenticated leaderboard callable returns only canonical rows whose document ID, embedded user ID, optional subject ID, and live `users/{uid}` backing agree. Authoritative gameplay, race, analytics, receipt, and content records are also server-only ([Firestore rules](../firebase-functions/firestore.rules#L20-L35), [leaderboard rule](../firebase-functions/firestore.rules#L123-L130), [callable filter](../firebase-functions/src/gameplay/leaderboard.ts), [server-only rules](../firebase-functions/firestore.rules#L132-L183)).

#### Authoritative single-player gameplay

- Private `users/{uid}/singlePlayerSessions` records contain mode, riddle/content/completion IDs, locale, the canonical answer, attempts, last submitted guess and result, continue/hint/skip state, hashed request inputs and replay results, terminal state, and timestamps ([session type](../firebase-functions/src/gameplay/singlePlayerSessionTypes.ts#L31-L75), [write path](../firebase-functions/src/gameplay/singlePlayerSession.ts#L42-L58)).
- Session tokens and content keys are hashed for Firestore document IDs. Sessions and their binding records receive one fixed expiry 30 days after issue; server reads reject expired state even before asynchronous TTL deletion ([session issue](../firebase-functions/src/gameplay/singlePlayerSession.ts#L69-L143), [expiry enforcement](../firebase-functions/src/gameplay/singlePlayerSessionExpiry.ts#L5-L30)).
- `gameCompletionReceipts` link the Firebase UID, mode, completion key, outcome/reward response, and timestamp to replay-safe progression. Loss receipts expire after 45 days. Correct-completion receipts have no TTL while the account exists, because they guard permanent progression/reward replay ([completion receipt](../firebase-functions/src/gameplay/completeGameLogic.ts#L173-L215), [TTL constant](../firebase-functions/src/gameplay/completeGameLogic.ts#L64)). Account deletion explicitly removes both kinds.
- The user profile accumulates coins, progression, win/guess/streak/score statistics, daily dates/keys, and achievements ([completion update](../firebase-functions/src/gameplay/completeGameLogic.ts#L283-L390)).

#### Multiplayer and data visible to other players

- Race runs store the owner's Firebase UID, challenge/rivalry IDs, locale/category, answer-bearing riddle snapshots, guesses-used/hints/revealed letters, clocks/penalties, ghost events, results, and optionally an opponent display-name/avatar/timing snapshot. New opponent snapshots also carry a server-only `subjectUserId`; it is never included in the response. A stored legacy opponent name/avatar without that subject link is projected only as the generic “Riddle Quest player” with no avatar ([race record and projection](../firebase-functions/src/race/raceEngine.ts)). Runs, decks, challenges, attempts, start requests, and nested request receipts are configured with a seven-day expiry ([race TTL](../packages/core/src/race/raceSchemas.ts#L17-L20), [race writes](../firebase-functions/src/race/raceService.ts), [committed TTL policies](../firebase-functions/firestore.indexes.json)).
- New identity-bearing race mutation receipts store only a generic opponent label and no avatar at rest. Their expiry is capped to the parent run's persisted expiry. Cached replay first requires that live parent and verifies its owner; it then hydrates only the parent's current linked, privacy-safe opponent projection. A missing parent returns `not-found`, and a parent whose subject link was removed keeps the generic projection, so an orphaned or post-deletion receipt cannot replay a stored name/avatar ([receipt minimization](../firebase-functions/src/race/raceReceiptPrivacy.ts), [transactional replay](../firebase-functions/src/race/raceService.ts)).
- A published challenge exposes its creator's display name, avatar URL, category, time to beat, rules and expiry to another authenticated, race-enabled player who has the challenge ID ([preview schema](../packages/core/src/race/raceSchemas.ts#L304-L324), [authenticated callable](../firebase-functions/src/race/raceCallables.ts#L161-L167)). The server record also contains creator UID, riddle IDs, timing/penalties and ghost events ([challenge record](../firebase-functions/src/race/raceSetupService.ts#L29-L73)).
- A race inbox entry is stored under the challenge creator's user document and contains the challenger's display name, optional avatar URL, category, result, timing delta, read state, timestamp, seven-day `expiresAt`, and `opponentUserId`. The provider-neutral Firebase UID is returned only for a still-linked known rival so the owner can invoke server-authorized block/report actions; it is not a raw Jest or Meta player ID. The expiry is omitted. Deleted or unlinked subjects receive the generic name/no-avatar projection and no target UID ([inbox write](../firebase-functions/src/race/raceService.ts), [public projection](../firebase-functions/src/race/raceReadService.ts), [inbox schema](../packages/core/src/race/raceSchemas.ts), [TTL/index policy](../firebase-functions/firestore.indexes.json)).
- Blocks are stored under the reporting user's `blockedRivals` subcollection after a transactional known-rival check. Categorized reports contain reporter/target Firebase UIDs, one fixed category, status, and timestamp in the server-only `socialModerationQueue`; no free-form text, platform name, or photo is accepted. Report IDs are request-idempotent and each reporter is capped at five unique reports per UTC day.
- Accepting a challenge re-reads the challenge and its creator's permanent deletion guard in the same Firestore transaction that creates the challenger run. A creator deletion that races the earlier preview therefore prevents a new identity snapshot from committing ([transactional start](../firebase-functions/src/race/raceService.ts)).
- The permanent deletion guard remains the authority after a run starts. Mutation, cached replay, resume, duplicate-start, and publish paths transactionally check a linked opponent and physically replace a tombstoned or unlinked identity with the generic name and no avatar/subject link before writing. A finishing challenger separately checks the challenge creator's guard in the same transaction and skips the inbox and creator-achievement writes when it exists. Challenge previews check the creator guard, and inbox pages batch-check their bounded set of opponent IDs; both return and persist the generic projection for a tombstoned subject ([opponent privacy resolver](../firebase-functions/src/race/raceOpponentPrivacy.ts), [canonical settlement](../firebase-functions/src/race/raceSettlement.ts) and [idempotent delivery](../firebase-functions/src/race/raceSettlementDelivery.ts), [read projections](../firebase-functions/src/race/raceReadService.ts)).
- Leaderboard rows expose the stable Firebase UID, username, optional avatar URL, level, XP, total wins, best streak, and update time through an authenticated callable; responses are capped at 100 rows. New rows use the Firebase UID as both document ID and server-only `subjectUserId`. The callable suppresses orphaned and noncanonical historical rows and verifies a live profile with bounded Admin reads; it never treats a matching name or avatar as proof of ownership. Direct client reads are denied ([row projection and live-user filter](../firebase-functions/src/gameplay/leaderboard.ts), [Firestore rule](../firebase-functions/firestore.rules#L123-L130), [Firebase client response](../packages/portal/src/firebase.ts#L157-L172)).
- Race analytics stores an allowlisted event name/parameters plus a stable salted SHA-256 cohort hash of the Firebase UID. It omits the direct UID and expires after 30 days ([event fields](../packages/core/src/race/raceAnalyticsSchemas.ts#L6-L23), [storage](../firebase-functions/src/race/raceRollout.ts#L33-L38), [write/expiry](../firebase-functions/src/race/raceRollout.ts#L72-L95)).

#### Avatars

- A registered Jest player's SDK avatar URL fills an empty game profile avatar automatically. The callable checks the matching Jest identity, requires an HTTPS URL, and preserves an avatar already chosen by the player ([client](../packages/portal/src/jest/JestPlayApp.tsx), [server](../firebase-functions/src/profile/syncJestAvatar.ts)). This stores a provider-hosted URL, not a copy of its image bytes. Account deletion removes the saved URL from the game profile and leaderboard, but cannot recall images already shown in another player's cached race view.
- Registered Jest players can select a JPEG, PNG, or WebP up to 5 MiB. The browser center-crops it to 256 by 256 pixels and re-encodes those pixels as a WebP of at most 512 KiB, so the original file is not uploaded ([browser preparation](../packages/portal/src/play/avatarImage.ts#L1-L68)). The server accepts at most 512 KiB and validates the declared type and file signature ([decoder](../firebase-functions/src/profile/avatarUpload.ts#L1-L29)).
- The object is stored at `avatars/{uid}/profile` with a download token and `Cache-Control: public,max-age=86400`; its tokenized download URL is saved to the profile and leaderboard ([upload](../firebase-functions/src/profile/updateAvatar.ts#L14-L49)). Anyone who obtains the tokenized URL can fetch the image, including through leaderboard/race display. Storage SDK reads are otherwise denied by rule ([Storage rules](../firebase-functions/storage.rules#L1-L10)). Deletion removes the object, but the code cannot recall copies already shared and does not invalidate already-cached content before its configured 24-hour cache lifetime.

#### Purchases, subscriptions, and referrals

- Facebook commerce currently has a server-internal verified-input ledger but deliberately no externally reachable grant/refund endpoint until Meta's real signed purchase and raw webhook fixtures are captured. `facebookCommerceReceipts` stores provider, Firebase UID, product/kind, purpose-scoped payment/token hashes, gross/net coin accounting, purchase time, and refund time. `facebookCommerceAccounts` stores hidden coin debt and the remove-interstitial entitlement; `facebookCommerceRefunds` stores the linked hashed purchase receipt and refund accounting. Firestore clients cannot read or write any of these collections. Account deletion removes the live account record and replaces UID-linked receipt/refund records with identity-free replay tombstones. A later verified refund updates/creates only identity-free replay tombstones; it cannot recreate the user, balance, debt, or entitlement ([ledger](../firebase-functions/src/facebook/facebookCommerceLedger.ts), [rules](../firebase-functions/firestore.rules)).
- Facebook referral entry data contributes only a 43-character opaque token. The server stores its hash with inviter UID and seven-day issue/expiry times, then stores one immutable invitee/inviter binding after authenticated App Check. New tokens carry an exact Firestore TTL timestamp, and bindings retain the issuance window so matching retries survive temporary-token cleanup. A bounded atomic legacy backfill is prepared; neither backfill nor the committed TTL policy has been deployed/accepted in the 2026-10-01 read-only check. Daily cap records contain inviter UID, UTC day, and count. First-win settlement receipts store both UIDs, two reward amounts, and settlement time while the account exists. Deletion removes active tokens/bindings/caps and anonymizes settlement receipts to reward/time replay evidence ([referral authority](../firebase-functions/src/facebook/facebookReferrals.ts), [entry parser](../packages/portal/src/facebook/referrals.ts)).
- Signed purchases update the user's coins, purchase flag, login time, and first-purchase achievement. New `jestPurchaseGrants` records store a SHA-256 purchase-token hash as both document ID and field, SKU, coin value, timestamp, and replay-protection flag; no raw token or direct UID is written in the current format ([purchase grant](../firebase-functions/src/jest/jestEndpoints.ts#L233-L318), [hashing](../firebase-functions/src/jest/jestPurchaseReceipts.ts#L1-L23)).
- Signed subscription state writes `hasActiveSubscription`, active SKU values, verification timestamp, and login time to the user profile ([subscription sync](../firebase-functions/src/jest/jestEndpoints.ts#L325-L365)). Production UI exposure and provider billing records are Jest concerns; this is the game's entitlement copy.
- Referral verification receives Jest-signed inviter/invitee platform IDs, registration timestamps, and eligible references. It deduplicates conversions by invitee; `joinedAt` is validated but not persisted by current writes ([conversion parser](../firebase-functions/src/jest/jestReferralReceipts.ts#L17-L73)).
- A latest `jestReferralVerifications` checkpoint stores reference labels, conversion count, and verification time under a document ID derived from the inviter's player ID. Each granted pair creates a permanent `jestReferralRewards` replay receipt under a deterministic SHA-256 ID derived from both platform IDs; the current receipt body contains only reference, reward amounts, timestamp, and replay flag ([referral grant](../firebase-functions/src/jest/jestEndpoints.ts#L368-L461), [receipt IDs](../firebase-functions/src/jest/jestReferralReceipts.ts#L46-L55)). Although raw IDs are absent from the current receipt body, the deterministic pair-derived document ID remains a pseudonymous linkability artifact and is retained for replay protection.
- Referral reconciliation can create a synthetic Riddle Quest Firestore user profile and award coins for a referred player before that player starts their own Firebase session ([referred-user creation](../firebase-functions/src/jest/jestEndpoints.ts#L397-L443)). **Owner/counsel decision:** define how an invited non-returning player's game-side record is surfaced in access/deletion workflows.

#### Sentry

- Browser Sentry starts only for a remote production build with an HTTPS DSN. It captures uncaught failures, unhandled rejections, and explicitly reported caught exceptions at a 100-percent error sample rate. It sets `sendDefaultPii: false`, samples zero performance traces, does not capture console warnings/errors as standalone events, and removes the default breadcrumb, browser-session, conversation, culture, and HTTP-context integrations ([browser setup](../packages/portal/src/observability/sentry.ts)).
- Browser redaction removes values under sensitive key names, bearer/JWT/image payloads, URL queries/fragments, and free-form message fields while retaining stack frames and bounded structured diagnostics. Its final event boundary also drops ambient SDK `request`, `user`, `contexts`, and breadcrumb fields rather than relying only on `sendDefaultPii` ([browser redaction](../packages/portal/src/observability/sentryPrivacy.ts)).
- Function Sentry is enabled when `SENTRY_DSN` is configured, uses `sendDefaultPii: false`, captures errors at 100 percent, samples zero performance traces, applies analogous key/message, credential, image, and URL query/fragment redaction, and removes the same ambient request/user/context/breadcrumb fields before delivery ([function setup](../firebase-functions/src/shared/sentry.ts)).
- Sentry organization/project region, retention, access roster, alert integrations, and deletion/export behavior are not in the repository. A production envelope review is also required to confirm the final SDK-generated metadata after redaction.

Historical race snapshots whose challenge/run/attempt linkage has already expired cannot be attributed safely to a particular deleted subject. The application therefore fails closed: any opponent snapshot without the new server-only subject UID is returned with a generic player label and no avatar. ## Account deletion reality

The in-game Profile flow calls an authenticated Firebase Function and, after success, signs out Firebase ([client service](../packages/portal/src/play/firebaseServices.ts#L168-L181), [callable](../firebase-functions/src/profile/accountDeletion/deleteAccountCallable.ts#L8-L23)). The server currently:

1. writes the permanent pseudonymous Firebase-UID deletion guard before any identity-linked cleanup starts, then conditionally disables/minimizes or creates the retained Auth sentinel for a deterministic Jest UID; for every UID it returns a retryable failure rather than sweeping while any earlier authenticated callable lease remains, even after that lease's diagnostic deadline;
2. deletes subject-linked race inbox snapshots in other users' trees; first anonymizes the parent opponent projection, then nested legacy replay receipts, then the subject lookup in other users' runs; and uses still-present challenge/run/attempt links for best-effort legacy cleanup before those owned lookup records disappear;
3. deletes directly owned documents from listed legacy analytics/notification/progress collections, race runs and their nested replay receipts, challenges, start requests, attempts, race analytics, tutorial state, and completion receipts; then performs an indexed collection-group sweep by receipt owner UID to catch orphaned receipt subcollections whose parent run was already TTL-deleted;
4. converts legacy UID-linked Jest purchase grants plus Facebook and Reddit commerce receipts/refunds to permanent hashed replay tombstones, and deletes the live provider debt/entitlement accounts;
5. deletes the latest Jest referral-verification checkpoint, removes explicit platform IDs from legacy Jest referral receipts, deletes active Facebook referral tokens/bindings/caps, and anonymizes Facebook settlement receipts;
6. deletes the username reservation, canonical leaderboard row, and subject-linked noncanonical leaderboard rows;
7. recursively deletes `users/{uid}` and its subcollections;
8. deletes `avatars/{uid}/` and `exports/{uid}/` Storage prefixes; and
9. retains the disabled/minimized Firebase Auth sentinel only for deterministic Jest identities; every other Firebase Auth user, including a deterministic Facebook UID and a historical non-deterministic UID, is deleted, while the permanent Firestore guard remains to reject still-valid old ID tokens at every current authenticated callable ([server implementation](../firebase-functions/src/profile/accountDeletion/deleteAccountData.ts), [guard/lease implementation](../firebase-functions/src/jest/jestAccountDeletion.ts), [Auth sentinel](../firebase-functions/src/jest/jestDeletedAuthUser.ts)).

Before the server request starts, the client persists and verifies an `authoritative-deletion-pending` phase and rotates a local deletion generation. Current-build tabs on the same origin dynamically stop app-owned SDK and host-service work; a shared Web Lock drains operations that were already in flight before the authoritative delete runs exclusively. If the response is lost or the tab closes, startup obtains a fresh signed Jest assertion and calls a dedicated deletion-only HTTP retry. That endpoint idempotently runs the authoritative deletion directly and never mints Firebase credentials. After confirmed server success, the marker advances to `client-cleanup-pending`; every known app-owned Jest notification identifier is attempted, exact SDK/browser state is cleared, and startup terminates instead of recreating the account. A normal current-build startup for a tombstoned identity receives the stable `account-deleted` response before Firebase authentication and also terminates into cleanup. Any marker, notification, SDK flush, browser cleanup, or authoritative-retry failure remains retryable and cannot produce false success ([dedicated retry endpoint](../firebase-functions/src/jest/jestEndpoints.ts), [backend client](../packages/portal/src/jest/backend.ts), [retry-safe cleanup](../packages/portal/src/jest/accountDeletionCleanup.ts), [cross-tab gate](../packages/portal/src/jest/notifications/operationGate.ts), [Jest app integration](../packages/portal/src/jest/JestPlayApp.tsx)).

The permanent server guard applies across devices, origins, and client versions. It blocks recreation of a deterministic Jest Firebase identity through the normal game endpoints, and every current authenticated callable rejects a still-valid token for a deleted historical Firebase UID. Client-side coordination is still origin- and version-scoped: a tab on another origin or device, or an already-open older artifact that does not implement the marker/Web Lock protocol, cannot be drained or made to run cleanup by the deleting tab. The repository also cannot establish whether deleting Jest SDK keys or unscheduling identifiers on one client propagates across all Jest devices/provider stores. Account-deletion/protocol releases therefore still require the documented maintenance cutover and reload of legacy tabs, plus an authoritative Jest answer for cross-device SDK cleanup; source code cannot make that external mixed-version boundary atomic.

The current deletion operation does **not** establish all-data erasure:

- It does not delete the separate Jest player identity/profile, Jest analytics, platform purchase/subscription records, referral shares, or recipient copies.
- It cannot retract already delivered notifications or delete Jest's platform-side notification history. Pending current and legacy D1-D7 engagement and race reminders are explicitly unscheduled.
- It does not target historical Google Analytics records, Sentry, Firebase/GCP logs, reCAPTCHA/App Check records, provider backups, or support email. The committed Jest build does not create new game-configured GA records.
- The permanent pseudonymous game-account deletion guard, disabled/minimized Auth sentinel, and permanent purchase/referral replay receipts remain as described in the retention table.
- Facebook deletion also retains the server-only provider identity mapping, including the raw game-scoped Meta player ID and app ID, while clearing the active Firebase UID. Existing identity nonce rows are not part of account cleanup.
- New cross-user race parent snapshots are deleted or anonymized through their server-only subject UID, while new identity-bearing mutation receipts never store the copied name/avatar. Legacy snapshots with a surviving challenge/run/attempt link receive the same cleanup, including nested receipt minimization before the link is removed. A legacy parent whose links already expired cannot be attributed to one subject, so current responses suppress its stored identity; the operator migration anonymizes all existing-parent receipts and deletes parentless receipts at rest. Production must not claim the at-rest migration completed without its recorded aggregate result.
- Orphaned/noncanonical legacy leaderboard rows are not exposed by the callable or direct Firestore access. Production must not claim they were purged at rest until the bounded leaderboard migration has a reviewed aggregate result.
- A cached avatar or image already included in a share cannot be recalled by deleting the Storage object.
- Firestore rules still name legacy `userClassicProgress`, `userDailyChallengeAttempts`, and `tutorialProgress` paths, but no active writer was found in the current tree. The deletion routine now idempotently removes matching progress records and the direct tutorial document so historical data in those documented shapes is covered ([legacy rule paths](../firebase-functions/firestore.rules#L62-L97), [deletion inventory](../firebase-functions/src/profile/accountDeletion/deleteAccountData.ts)). **Production verification required:** inspect whether historical deployments used any different field or document shape.
- The same still-existing Jest identity is permanently blocked from recreating a Riddle Quest Firebase user. This does not delete the Jest platform identity or prove that app-owned Jest SDK data, pending notifications, analytics, shares, purchases, or recipient copies were removed across every device and provider store.
- The permanent tombstone and callable-lease invariant now apply to every authenticated Firebase UID, including historical non-deterministic identities; only the disabled-Auth sentinel is specific to deterministic Jest UIDs. Before release, still run an exact-production aggregate audit across Firebase Auth and every UID-bearing game collection, reconcile or retire identities outside the current deterministic Jest pattern, and verify no historical HTTP endpoint or identity issuer that bypasses the current callable wrapper remains deployed. This audit is needed to find legacy data shapes and retired surfaces, not to make current authenticated callables honor the guard.

Counsel-facing copy must distinguish “delete my Riddle Quest game data” from deleting the Jest platform account and must accurately disclose the exceptions that the owner chooses to retain or remediate.

## Recorded matchmaking and settlement

- `raceMatchCandidates` stores game-owned creator linkage, provider pool, language/category, immutable content/rules revision, fixed recording performance and expiry. It contains no answers or provider profile payload. It is a non-authoritative accelerator; discovery and acceptance consult the canonical challenge and account/block/attempt records.
- `raceMatchOffers` stores requester linkage, request fingerprint, challenge reference, a 60-second discovery-cache expiry and seven-day storage TTL. New receipts also retain answer-free policy/confidence/performance/read-cost metadata plus accepted-run, scheduled-start and terminal facts for funnel/calibration measurements. Provider profiles are hydrated after selection and are not copied into receipts. Clients receive only the opaque offer reference and permitted challenge preview. Account deletion removes requester-owned offers; delayed projection writes never recreate missing receipts.
- Versioned terminal matchmaking logs classify matched/replayed/empty/capped/failed invocations, with stable failure reason, elapsed time and read/query/callback counters. Answer-free start-command observations separately report returned/failed invocation, bounded provider/language/entry kind, response status/category when available, broad failure code and elapsed server time. They omit account, offer, challenge, run and request identifiers and error payloads; duplicate commands remain separate observations. Success/replay logs retain validated policy hash/revision; they do not include request, player, run, question or answer payloads. The guarded benchmark writes only a dedicated loopback-emulator demo project and emits aggregate synthetic measurements.
- Terminal offer attribution distinguishes full ten-answer finishes from partial/idle losses and abandonment. Complete finishes alone retain actual normalized duration, prediction log error and adjusted-time gap against the fixed ghost; settlement delay uses original persisted clocks. The backend-only calibration command reports bounded aggregate cohorts through an answer/identity field allowlist and has no database mutation path. Offline candidate/profile inputs remain operator-local and are never emitted in comparison reports.
- New offers retain the validated selection policy snapshot, algorithm/revision/hash, selected and baseline recent-rival counts/question-overlap fractions, baseline performance band and a freshness-relaxation flag for reproducible calibration. These fields contain no answers or provider profiles. `raceConfig/matchPolicy` is an admin-only configuration of language/category priors, confidence/windows, ranking weights and bounded freshness parameters; client access is denied.
- Optional experiments retain ID/revision/arm/allocation hash in offers and aggregate reports; their allocation salt remains in admin-only configuration. Deterministic assignment uses the existing authenticated identity without creating another player registry. Experiment metadata contains no player identity, answers or salt, and requester-owned offers retain existing deletion/TTL handling. Reports explicitly use offer observations rather than independent-player significance or causal-lift estimates.
- `raceSettlementOutbox` stores run/participant references, canonical result, presentation time difference and delivery state for bounded retention. Delivery rechecks deletion and blocks transactionally, uses current permitted game-owned presentation, and has an exact-once reward/inbox receipt. Account deletion removes participant-linked outbox events and creator-linked candidates, and requester-owned offers. Delayed jobs never recreate deleted accounts.
- Race run settlement fields retain the canonical outcome and reward/presentation markers for the same bounded run lifetime. No new browser analytics are enabled; matchmaking diagnostics contain aggregate counts, pool language/provider, rejection categories and request duration, without player IDs, guesses, or answers.
- `raceMatchProfiles` is a private owner/language projection of overall/category log-duration estimates, separate censored lower-bound evidence, role/category completion counts, confidence evidence/timestamps, bounded viewer-specific opponent hashes and canonical riddle exposure IDs. Version 2 profiles distinguish observed finishes from partial races; legacy mixed confidence is limited during lazy migration without inventing completion counts. Acceptance records preloaded exposure, including abandoned attempts; settlement updates only the attempt owner. Observation clocks use canonical finish time, with settlement-time fallback for legacy records. Account deletion removes the owner's subcollections. `racePerformanceOutbox` retains the owner/run linkage and processing receipt for the bounded settlement delivery period and is removed on owner deletion.
- `raceDeadlineFailures` stores an opaque run reference, processing state, original indexed deadline, quarantine/replay times and a generic failure code. It carries no names, avatars, answers or provider identity payloads. Diagnostic receipts expire after 90 days and are removed alongside account-owned runs. Operator logs identify the opaque run/event requiring repair; they do not include its answer-bearing validation details.
- `raceMaintenance/projectionReconciliation` is a server-only operational checkpoint containing a collection phase, last document-ID cursor, random worker lease, timestamps, bounded count report and generic failure code. It contains no account IDs, profile payloads, questions or answers. The cursor may reference a challenge document; repeated passes overwrite it. `raceConfig/maintenance` provides the explicit projection-reconciliation opt-in. Neither collection is exposed directly to clients.

Recovery overwrites these global checkpoints; they contain no copied account/profile/question/answer payloads. Explicit outbox state, attempt, next-retry, quarantine and replay metadata retain the original receipt TTL. Validated administrator replay never recreates missing source/account data or extends retention.

Projection diagnostics additionally expose maintenance enablement, valid page/full-cycle ages, retained page failure and current/previous-cycle unavailable observations; cursor and lease identities remain private. They contain no account identities, event payloads, questions or answers. Handle these under the existing operational logging retention policy. Operator repair commands identify only the selected project, collection and opaque event, and validators return answer-free errors.


- New recorded match offers and challenger runs retain a private SHA-256 `recordingFingerprint` for source consistency through issuance, preparation and readiness. Its input binds existing recording identity/content/scoring facts; no raw creator identity or answers are added by this field. The digest remains a pseudonymous link to the issued recording, follows its parent receipt/run retention and deletion handling, and is excluded from client views and lookup telemetry. Equivalent presentation anonymization does not change it. Historical records without the digest remain supported without inferring missing provenance.
