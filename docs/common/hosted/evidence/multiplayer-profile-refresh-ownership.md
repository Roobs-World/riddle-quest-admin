# Multiplayer host profile refresh ownership

A real React browser harness reproduces a stale-account profile overwrite: an outstanding multiplayer profile load for owner 1 returns after owner 2 becomes current, and the old hook replaces the profile and sends an owner-1 auth bridge message. The baseline fails on this ownership assertion.

`useHostRaceCoordination` now retains a private lifetime tied to the authenticated UID and identity loader. Render-time ownership rejects old callbacks before effect cleanup; cleanup invalidates pending loads after unmount or replacement. A sequence counter makes the newest same-account profile refresh win. Balance and achievement callbacks are checked before later effects, and profile/bridge writes recheck ownership after each callback. The bridge uses the latest same-account user representation.

The browser regression gate covers account replacement, reversed same-account response ordering and unmount at 1280px and 390px, in both normal React and Strict Mode: twenty scenarios pass. It also invokes retained stale callbacks to ensure they cannot apply a new balance after account replacement or unmount. The harness now mounts both actual host hooks and additionally reproduces authentication changing before React renders the new account. That earlier guard failed because the stale callback applied a second coin balance during the interval. The authentication subscription now exposes synchronous account ownership, and multiplayer passes expected UIDs into queued balance/profile updates. A unit check also confirms ownership changes without a render and retired subscription callbacks are ignored.

The follow-up handler also previously ignored ownership loss after profile refresh. A handler baseline test and the browser harness reproduce that provider callback escaping its account. Multiplayer profile coordination now returns whether its account still owns optional follow-up, and the actual outcome handler skips the provider callback after an explicit false. Superseded same-account profile reads remain eligible for their own provider completion, so response ordering does not discard another valid race result. Handler tests cover false, true and legacy void responses; browser assertions cover all twenty lifecycle scenarios, including both same-account completions.

The provider callback sequence previously opened results even after its recording promise completed under a replaced account. Two baseline tests reproduce starting work without ownership and opening results after ownership changes during recording; the same-owner control passes. The production host now uses `deliverHostRaceResult` to check ownership before recording and after acknowledgment before showing results. Subscription account visits use private identity rather than UID equality alone: switching away and back invalidates prior scopes, while same-account profile notifications preserve them. A unit check and four additional browser cases cover this round trip, including changes batched before React commit.

The fixture uses independently controlled profile promises and fake users, with no provider or Firebase operation.

All 1,651 runnable client tests pass (97 tests remain skipped), along with portal types, security and scalability pass. All seven isolated target artifacts build and exact dependency evidence validates them, including the six required browser targets. Shared documented-declaration and file-size gates currently fail in the other chat's active subscription/E2E edits; this batch does not alter those files or record a completed dashboard receipt.

Logs and hashes are in `artifacts/race-profile-refresh-ownership/verification-held.json`. The new development manifest retains previous checks and adds this browser gate, for 48 checks. No Firebase deployment, Jest upload, activation or publication occurred. The multiplayer reliability audit remains active.
