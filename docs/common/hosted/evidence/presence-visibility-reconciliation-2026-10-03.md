# Presence permission reconciliation preparation — 3 October 2026

The [ordering fix](presence-visibility-ordering-2026-10-03.md) left a concrete hosted rollout requirement: reconcile existing legacy permission bits after older non-versioned writers drain. A bounded maintenance tool now prepares that step. It does not grant permission from an export or caller-supplied state. It accepts only an explicit directed-pair inventory and recomputes each active owner's permission through the existing server-authoritative mirror.

`firebase-functions/src/presence/presenceVisibilityReconciliation.ts` handles at most twenty entries. Preview reads stored RTDB permissions and returns aggregate counts without acquiring an operation lease or writing either database. Apply uses current rivalry and bilateral blocks. Stale edges for permanently deleted owners are removed only after their earlier operation leases drain; an old diagnostic expiry alone never proves completion. Cleanup removes just the selected permission and reverse hint. A busy entry returns the completed prefix so the operator can resume precisely. No account, Auth, source relationship, consent, entitlement or provider capability is changed.

`firebase-functions/scripts/presence-visibility-reconcile.js` requires an explicit project, matching approved default-database URL and absolute private inventory path. It validates the whole inventory offline, caps files at 2 MiB/5,000 pairs and pages at twenty, rejects duplicate or unknown fields/options and requires matching project confirmation plus the exact preview hash for apply. Demo mode requires both loopback emulator services; a live project with ambient emulator settings is rejected. The CLI returns no player identifiers or presence values, and sanitizes provider failures. Cursor/end fields describe only the requested input; they expressly do not certify global coverage or old-writer drain. The [staging runbook](../presence-visibility-reconciliation.md) describes inventory provenance and the actual commands.
