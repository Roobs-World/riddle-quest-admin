Product + engineering implementation plan

Race to 10: Recorded Ghost Duels

Let a player record a category-specific run, share it, and let a friend race the real performance later as if the contest were unfolding live. The first player to solve ten riddles wins.

Status: implementation in progress; production flag off · Plan date: 31 July 2026 · Target: Jest HTML5 · Launch scope: English only

1. Outcome and product thesis

Race to 10 should become Riddle Quest's primary friend-challenge loop. It creates real competitive pressure without requiring simultaneous availability, matchmaking supply, sockets, or reconnection logic. The opponent is a replay of a genuine, server-verified run—not a simulated player.

Player promise

“Pick your strongest category, set a real time, and dare a friend to reach ten before your ghost.”

Growth loop

Record → share → friend races → result changes hands → loser records a rematch → share again.

Technical principle

Firebase owns identity, deck selection, answers, timestamps, results, replay data, and rewards.

MVP recommendation: ship asynchronous recorded duels only. Preserve the “live” presentation, but label the opponent as a recorded run so the experience is exciting without misleading players.

2. MVP rules

Rule MVP decision Reason
Win condition First to 10 correct riddles Simple, readable, and ideal for a progress race.
Deck 15 canonical riddles from one category Allows different players to skip different hard riddles.
Order Identical canonical order for both runs Protects perceived fairness.
Run cap 5 minutes of adjusted race time Keeps links quick to play; hint and skip penalties count toward the cap.
Guesses Maximum 5 guesses per riddle Matches the established board pattern and limits brute force.
Skip Manual after one guess or automatic after five wrong guesses; either adds 45 seconds A deliberately heavy cost prevents players from cycling through the deck for easy riddles.
Hints One per riddle; reveals one server-selected letter; adds 15 seconds Hints remain useful, but the time cost can materially change the result.
Penalty clock Adjusted time = server wall time + 15 seconds per hint + 45 seconds per skip The opponent ghost moves forward when a penalty is applied, making the disadvantage immediately visible.
Paid continues Disabled Competitive results must never be purchasable.
Pause The authoritative clock continues while hidden or disconnected Prevents pausing for extra thinking time.
Expiry Challenge accepts new attempts for 7 days Creates urgency and aligns with Jest's notification horizon.
Attempts One ranked attempt per player per challenge Keeps the initial comparison meaningful; practice is unranked.
Tie Earliest server-recorded adjusted tenth-solve time wins Deterministic and server-verifiable.

Initial penalty values are server-configured and frozen into race10_v1 challenge records. Race hints do not spend coins: every player receives the same hint allowance and pays through adjusted time. If the creator fails to reach ten before five minutes of adjusted time, the run is saved as incomplete but cannot be published.

3. End-to-end player journey

Choose Race to 10
Pick category
Record a run
Publish challenge
Share Jest link
Friend races ghost
Share or rematch

Creator path

  1. Select Race to 10 from the game-mode surface.
  2. Choose an available category and review the rules.
  3. Start after a three-second countdown.
  4. Solve ten; hints add 15 seconds and skips add 45 seconds to the server-owned race clock.
  5. Review the run and publish it as an immutable challenge.
  6. Share a personalized result card and referral link.

Recipient path

  1. Open the link and land on a challenge preview, not the home screen.
  2. See challenger, category, ten-riddle goal, adjusted time to beat, and expiry.
  3. Start the same canonical deck after a countdown.
  4. Watch the recorded opponent progress against the live attempt and surge ahead after penalties.
  5. See an authoritative win/loss comparison.
  6. Record a counter-challenge or share the victory.

4. The ghost replay model

Store competitive milestones rather than keystrokes or answers. On replay, the UI advances the ghost's score whenever the player's adjusted race clock crosses a recorded milestone. A hint adds 15 seconds and a skip adds 45 seconds to that clock, so the ghost visibly surges ahead when either penalty is taken.

Playback behavior

  • Anchor animation to the attempt's server-issued start time.
  • Use performance.now() only for smooth display between server syncs.
  • Display both the added penalty and the new adjusted time when a hint or skip is accepted.
  • Fast-forward the ghost against adjusted time after a penalty; animate the catch-up rather than teleporting silently.
  • When a tab resumes, jump the ghost to the correct current milestone.
  • Never pause the authoritative clock on visibility change.
  • Stop immediately when the player or ghost reaches ten.
  • Expose only event type, adjusted time, penalty amount, and cumulative score to the opponent.
  • On the result screen, show the transparent calculation: wall time + hint penalties + skip penalties = adjusted finish time. 
type GhostEvent = {
  sequence: number;
  type: "correct" | "hint" | "skip";
  riddlePosition: number;
  wallElapsedMs: number;
  penaltyAddedMs: 0 | 15000 | 45000;
  totalPenaltyMs: number;
  adjustedElapsedMs: number;
  correctCount: number;
};
Penalty behavior: the backend calculates and returns the new adjusted time. The client never adds a local-only penalty. If the adjusted clock crosses the ghost's next milestone—or the five-minute run cap—the backend result wins and the UI catches up to it.
Latency policy: v1 uses backend receipt time for competitive milestones. This is harder to manipulate but includes network latency. Measure p50/p95 submission latency before considering a bounded, server-validated client timestamp in a later integrity version.

5. Categories and content preparation

The current Firestore category field represents content mode values such as classic and daily. Keep gameMode for mode and introduce a separate, stable categoryId for subject taxonomy.

Launch category ID Content focus
History history People, events, civilizations, and eras from the past.
Geography geography Countries, cities, landmarks, borders, and the world.
Music music Artists, songs, instruments, genres, and sounds.
Film film Movies, characters, actors, directors, and cinema.
Science science Discoveries, nature, space, experiments, and technology.
Mixed mixed A dedicated varied pool spanning the five subject areas.

Content model requirements

  • Launch in English only; retain a stable canonicalRiddleId for possible future translations.
  • Add categoryId, difficultyBand, raceEligible, and qualityVersion.
  • Build each deck from comparable difficulty bands rather than fifteen unrestricted random riddles.
  • Never generate content during a race. Use pre-generated, validated pools.
  • Enable each of the six English categories only when it has exactly 30 approved, race-eligible riddles.
  • Every answer must respect the existing game-wide limit of seven characters.
  • Mixed is its own 30-riddle pool; it does not aggregate the other five pools.
  • Do not expose Race entry outside English until translated content is explicitly added and reviewed.
Fairness risk: trivia familiarity varies even within English. Track performance by canonical riddle and category, exclude outliers through a new quality version, and do not add other locales until their difficulty has been reviewed independently.

6. Authoritative backend design

Add dedicated race collections and expose them only through callable Cloud Functions. Firestore clients must not read decks, answer-bearing documents, raw opponent events, or writable competitive state directly.

Collections

  • raceCategories/{categoryId} — server-managed availability and pool versions.
  • raceDecks/{deckId} — immutable canonical sequence and content version.
  • raceRuns/{runId} — owner, active position, guesses, milestones, integrity status.
  • raceChallenges/{challengeId} — immutable published creator run and expiry.
  • raceAttempts/{attemptId} — recipient run and authoritative comparison.
  • users/{uid}/raceInbox/{itemId} — outcome/rematch items visible to one player.

Indexes and lifecycle

  • Index inbox by createdAt desc and challenge attempts by challenge/player.
  • Use idempotency keys for create, submit, hint, skip, publish, and rematch operations.
  • Apply Firestore TTL to abandoned runs and expired challenge operational data.
  • Retain compact aggregate results separately if product analytics requires them.
  • Version rules, scoring, content pool, and replay integrity on every run.
raceChallenges/{challengeId} {

  categoryId: string,
  deckId: string,
  targetCorrect: 10,

Public callable responses must return a redacted view. A challenge preview may expose the challenger snapshot, category, adjusted time to beat, target, and expiry; it must not expose deckId, future riddles, answers, or internal integrity fields.

7. Callable function contract

Callable Purpose Key validation / response
listRaceCategories Return categories enabled for the current locale. Return IDs, localized-key references, art tokens, and pool availability only.
startRaceRun Create a creator run or challenge attempt. Verify identity; validate category/challenge; select or reuse deck; return run ID, first clue, and server start.
submitRaceGuess Validate one guess and advance state. Require run ID, riddle ID, guess, and request ID; rate-limit; record server wall and adjusted time; return feedback and next clue if needed.
requestRaceHint Reveal one server-selected letter and apply the hint penalty. Enforce one hint per riddle; add 15 seconds idempotently; return the revealed letter, total penalty, and authoritative adjusted time. Do not spend coins.
skipRaceRiddle Advance after at least one submitted guess. Add 45 seconds idempotently, record the skip, return adjusted time, and advance without awarding progress.
resumeRaceRun Recover a reload or short disconnect. Return redacted current state, accumulated penalties, and authoritative adjusted time; never reset the clock.
publishRaceChallenge Freeze a completed creator run into a shareable challenge. Only the owner; must have ten verified solves; idempotently return the same challenge ID.
getRaceChallengePreview Render the referral landing experience. Accept opaque challenge ID; return redacted snapshot or expired/revoked state.
getRaceOutcome Return comparison and rematch eligibility. Only participating players; derive result from canonical runs.
listRaceInbox Show completed attempts and pending rematches on return. Owner-only, cursor-paginated, redacted opponent snapshots.

Race UI state machine

idle → categories → preparing → countdown → racing
                                      ↘ recovering
racing → won | lost | timed_out | disconnected
result → publish → share
result → counter_challenge → categories

Wrong guesses, hints, and skips remain within racing. Hint/skip controls stay disabled until the server returns the authoritative penalty and adjusted clock, preventing double taps from displaying or applying multiple penalties. Every network action must represent loading, success, retryable failure, terminal failure, and duplicate/idempotent completion explicitly.

10. Integrity, abuse prevention, and privacy

Required controls

  • Authenticate every callable; derive UID from verified Firebase auth, never request data.
  • Store answers only in server-readable riddle documents.
  • Validate run ownership, active riddle, deck position, and state transition on every mutation.
  • Use server timestamps and server-calculated penalties; reject submissions after adjusted-time expiry or completion.
  • Rate-limit guesses per player, run, IP signal, and riddle.
  • Normalize guesses using the same locale-aware rules as existing gameplay.
  • Make hint, skip, guess, and finalization request IDs idempotent so retries cannot duplicate penalties.
  • Reject impossible progress, out-of-order messages, and conflicting duplicate requests.

Privacy and display

  • Snapshot only the public display name and avatar needed for a challenge.
  • Do not expose Jest player IDs, Firebase UIDs, guesses, email, or answer text.
  • Add a server-side revoke path for moderation and account deletion.
  • Use neutral fallback names and avatars for guest/missing profiles.
  • Escape all names in DOM and canvas share rendering.
  • Expire operational replay data according to a documented retention policy.
Reward rule: do not add coins, category crowns, leaderboard placement, or achievements until the complete server-authoritative flow and idempotent grant path are tested. The MVP can award cosmetic, non-economic result labels while integrity data is gathered.

11. Localization, accessibility, and resilience

  • Add every new visible string to all supported locales before merge; do not fall back silently for shipped UI.
  • Keep category IDs stable and untranslated; the launch UI and content are English-only.
  • Announce score changes through a throttled ARIA live region; do not announce every animation frame.
  • Represent player/ghost progress with text such as “You 6 of 10, Craig 7 of 10,” not color alone.
  • Honor reduced-motion by replacing avatar bursts, screen shake, and progress trails with short fades.
  • Maintain keyboard, pointer, and touch parity; preserve visible focus and minimum touch targets.
  • Provide mute controls and avoid audio-only countdown or result signals.
  • On offline/reload, offer resume while the authoritative run is active; otherwise show the canonical result.
  • If share, screenshot, or notification scheduling fails, keep the completed run and offer a retry.

Detailed phase notes

These phases are ordered dependency slices. Each phase should land with tests and usable acceptance evidence; avoid building every backend layer before exercising the first complete vertical path.

Phase 0 — Freeze rules and fixtures MVP

  • Approve the rules in section 2 and version them as race10_v1.
  • Define shared Zod request, response, event, category, run, and challenge schemas.
  • Create deterministic test decks and ghost timelines for English.
  • Add a feature flag that defaults off outside the deterministic harness.

Exit: contracts and fixtures compile in core; malformed examples fail tests.

Phase 1 — Category-ready content MVP

  • Add semantic category and canonical translation fields without changing classic/daily behavior.
  • Write a migration/backfill tool and a dry-run report for existing riddles.
  • Build pool validation for exact size, duplicate answers, clue leakage, English content, and answer length.
  • Seed enough reviewed content for categories/locales enabled at launch.

Exit: the backend can deterministically build a valid 15-riddle deck from every enabled English category pool.

Phase 2 — Authoritative run recorder Server first

  • Implement start, submit, hint, skip, adjusted clock, resume, completion, expiry, and idempotency.
  • Add server-only collections, rules, indexes, rate limits, and structured diagnostics.
  • Prove that clients cannot select questions, forge elapsed/penalty times, or advance score directly.
  • Add emulator tests for duplicate, stale, concurrent, out-of-order, and post-expiry requests.

Exit: a test client can record a verified ten-solve timeline and safely recover it after reload.

Phase 3 — Creator experience Vertical slice

  • Add the mode entry, category picker, rules, countdown, race HUD, and result screen.
  • Connect the bridge and host-service contracts to the run recorder.
  • Add fake-service scenarios for success, wrong answer, hint, skip, penalty timeout, offline, resume, and duplicate response.
  • Add all visible strings to every supported locale.

Exit: a player can complete and review a creator run in the Jest harness with accessible controls.

Phase 4 — Publish, deep-link, and ghost replay Core loop

  • Implement immutable challenge publication and redacted preview.
  • Extend entry-intent parsing and direct routing for valid, absent, expired, malformed, and revoked IDs.
  • Build deterministic ghost playback, penalty fast-forward, visibility catch-up, and finish arbitration.
  • Create personalized share cards and the stable Jest referral campaign.
  • Preserve completed runs when share is canceled or fails.

Exit: sandbox player B can open player A's link, race the correct ghost, and receive the authoritative result.

Phase 5 — Rivalries and return loop Retention

  • Create owner-only race inbox items when an opponent completes an attempt.
  • Add rematch and “choose my category” counter-challenge flows.
  • Add safe generic return reminders for registered creators, with identifiers and entry attribution.
  • Add race funnel analytics and operational dashboards/alerts.

Exit: the original creator can return, see the result, and publish a counter-challenge without re-entering context.

Phase 6 — Hardening and release Release gate

  • Run the complete unit, function, integration, browser, localization, and accessibility matrix.
  • Test guest/registered and two-user referral behavior in Jest mock and sandbox environments.
  • Review latency, content difficulty, abuse signals, indexes, TTL, cost, and error budgets.
  • Verify the UI in a mobile browser and build the standalone Jest artifact.
  • Roll out behind the feature flag to a small cohort before general availability.

Exit: acceptance evidence in section 15 is complete and the standalone artifact passes sandbox review.

15. Definition of done

  • A player can choose an enabled category and record a valid first-to-ten run.
  • The recorded timeline is produced exclusively from server-validated events and server timestamps.
  • A published challenge is immutable, opaque in shared payloads, revocable, and expires correctly.
  • A recipient reaches the correct preview directly from a Jest referral link.
  • The recipient sees the same canonical English deck without silent substitutions.
  • The ghost score advances at the recorded milestones and catches up after visibility changes.
  • Each hint adds exactly 15 seconds, each skip adds exactly 45 seconds, retries cannot duplicate a penalty, and the adjusted clock can trigger the run cap or a ghost victory.
  • The backend determines winner, wall time, penalty total, adjusted finish time, and ranked-attempt eligibility.
  • Share cancellation or failure never loses a completed result.
  • Rematch and counter-category paths create a new immutable challenge.
  • Guests, registered users, missing profiles, invalid payloads, and expired challenges have complete UX.
  • Every visible string exists in every supported locale and RTL/reduced-motion behavior is verified.
  • No race collection or answer-bearing field is directly readable or writable by clients.
  • Automated suites, browser verification, standalone Jest build, and two-user sandbox acceptance pass.

16. Explicitly deferred

Keep these out of the first release until the recorded duel loop proves engagement and integrity:

  • Later True simultaneous multiplayer and matchmaking.
  • Later Four-player party races and tournaments.
  • Later Spectating, chat, reactions sent between players, or presence.
  • Later Player-authored riddles or unrestricted packs.
  • Later Competitive coin entry fees or purchasable advantages.
  • Later Cross-locale global category leaderboards.
  • Later Client timestamp compensation before latency evidence exists.
  • Later Multiple ranked retries against the same recording.
