# Alternating freshness measurement, 9 October 2026

The batching change reduced elapsed full backend matcher work in the synthetic repetitive-opponent fixture. Five alternating baseline/candidate pairs ran against the same private loopback Firestore emulator, reversing order each pair. Each variant run exercised all six scenarios and matched replays, five observations per phase: 500 measured lookups total. Every result gate passed, including actual seeded winner, exact receipt replay, policy attribution, expected budget failures and work bounds. Two separate CPU-profile runs preceded measurement and are excluded from these timings.

For freshness searches, the median of the five run medians fell from 140.75 ms to 69.60 ms. Baseline run medians ranged 132.45–158.28 ms; candidate medians ranged 67.72–73.18 ms. These ranges do not overlap. Every pair retained the deterministic work reduction from 167 to 107 median document attempts and 69 to 24 transaction read batches. Healthy dense, sparse, exclusion, empty and capped timing ranges overlapped; no timing gain is claimed for them. Their application read/batch counts stayed unchanged.

This measures `findRecordedRaceMatch` through its actual SDK transaction, candidate search, offer creation and replay paths. Fixture seeding and clearing are outside timing. Server authentication, HTTP/browser transport, cloud cold starts, real provider identities, production contention and index billing are absent. The first lookup of each worker can include initial connection setup; using within-run medians reduces that effect but is not an explicit per-lookup warm-up protocol. This supports a local backend fixture improvement, not a production or complete player-path latency estimate.

Separate V8 profiles cover whole worker processes, including initialization and fixture work, so they cannot precisely attribute only the timed interval. Baseline idle samples were 60.3%; candidate idle samples were 36.5%. Together with actual RPC-batch counts this is consistent with reduced storage waiting, rather than a CPU helper optimization. There is one sequential request generator and no offered-load saturation test. The observed environment had eight cores; pre-run load averages were 1.13, 1.96 and 1.44. No browser/network share of player latency was measured.

Both variants were compiled under pinned Node 22.23.1 from isolated source copies. The baseline substitutes the exact saved pre-batching matcher module; all other current source remains identical. Compiled JavaScript hashes prove only `race/raceMatchmaking.js` differs. Backend source and benchmark hashes were frozen before execution and verified afterward. Artifacts retain all ten measured reports, raw worker streams, separate profiles, hash inventories and cleanup evidence. All four emulator ports were confirmed closed and both owned temporary compiled variants removed after exit 0. `artifacts/freshness-alternating-2026-10-09/verify.py` checks the experiment.

Backend validation also comprises 1761 passing unit tests, types/lint, and all 88 current SDK suite paths across an interrupted 87-suite pass and isolated final Storage recovery, documented separately. No client artifact changed. This finishes the batching candidate's planned local measurements; nothing has been deployed, and production observation remains unavailable.
