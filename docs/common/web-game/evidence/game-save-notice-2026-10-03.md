# Visible Jest save recovery — 2026-10-03

The previous bounded recovery policy could exhaust its attempts while the player had no indication that progress remained unsaved. The Jest game now shows a translated, non-modal notice when failed saves cannot proceed or exhaust the automatic retry budget. Retry enters the existing durability queue. Its busy state remains visible until every latest dirty player projection and preference patch is acknowledged by the SDK. Players can continue editing their answer during that wait.

`PlayerSaveRecovery` exposes a stable external-store snapshot and subscription. Ordinary saves and transient failures remain quiet. An independent `PlayerSaveRecoveryLayout` subscription observes persistent failure without changing the Jest hook's stable controls or restarting provider initialization. Account replacement, disable and retirement clear the old owner's notice. Online/resume signals retain their existing bounded recovery policy. Offline Retry is disabled until connectivity returns.

The layout reserves a row above the game instead of covering controls. Retry retains a 44-pixel target and translated accessible name. At widths at or below 360 pixels, a retry icon leaves room for the message; the accessible name and title remain translated. All 16 supported locales contain the new message, and the existing translated Retry key is reused. No SDK signature, backend request, grant, identity, reward or purchase contract changed.

## Harness findings and limits

The injected save callback initially changed identity on each preference render, unlike the stable production callback. That caused a fixture-only auth resubscription/profile write to enter a deliberately held storage operation. The verifier now uses the production callback ownership pattern and a bounded observation timeout; the interrupted initial job is not counted as passing. The offline case also dispatches the actual browser offline signal instead of merely changing a property.

An early layout snapshot ran before ResizeObserver and animation-frame sizing settled. The final verifier advances that frame and explicitly checks Submit and bottom navigation in addition to keyboard visibility. Narrow German screenshots motivated the compact Retry icon. The final matrix passes against that final layout.

Firefox MCP's window-resize tool clamps the window to a minimum width of 500 pixels and includes browser chrome in its height. The recorded German game viewport is 500×568 and the Arabic viewport is 500×832, rather than the requested 280-pixel or 390-pixel emulation. The actual 280-pixel matrix is verified by Chromium. The first German Firefox screenshot records the initial clamped 500×494 viewport. Controls remain inside those Firefox viewports, but keyboard keys measure about 25.3 pixels at 500×494 and 29.6 pixels at 500×568; this is a remaining short-viewport playability candidate, not evidence of a 32-pixel Firefox minimum. Raw observations retain those measurements. The first owned harness server ended with signal 143 before the second Firefox page could load; its terminal state was confirmed before a replacement server was started. The replacement server was closed normally after the Arabic checks.

React subscriptions and lifecycle behavior were reviewed against the React best-practices skill. The Jest HTML5 SDK skill's adapter ownership and acknowledged durability requirements remain in force. No live provider sandbox or production latency was measured. Failed state remains in memory until the provider acknowledges it; the notice accurately asks players to keep the game open.

The broader improvement goal remains active. Remaining candidates include better short-viewport key sizing, equivalent recovery ownership for Facebook/Reddit persistence, and further asynchronous gameplay ownership checks.
