## Scope and system boundaries

This inventory covers the React game, its isolated Jest, Facebook Instant Games, Reddit Devvit Web, and YouTube Playables adapters, browser/platform storage, the Devvit gateway, Firebase client and Functions code, Firestore and Storage rules/indexes, Google Analytics initialization, Sentry initialization, and the OpenAI-backed riddle-generation service. It does not inspect live provider consoles, production databases, provider contracts, email records, or backups.

Data subjects represented by current flows include Jest guests and registered players, invited/referred Jest players (whose game profile can be created before first play), multiplayer opponents, and people who email the support mailbox. The source does not implement an age field or age-verification flow.

The native Android app has a separate [Android privacy notice and Data safety draft](../../android/android-privacy-and-data-safety.md). That inventory covers Firebase anonymous and Google-linked accounts, native FCM, Play Billing, Play Integrity and the Play Install Referrer handoff. Its local pending-entry record is separate from the backend referral settlement ledger. The Android draft remains unpublished, and real Play installation and payment verification remain open.

### Facebook Instant Games platform data

The Facebook target loads SDK v8 only in its own artifact. It reads the game-scoped player ID, requests signed player information bound to a one-use game nonce, uses asynchronous FBInstant player data for preferences/resume state, reports loading progress, calls `startGameAsync`, and flushes on pause. The signed assertion and raw game-scoped ID cross into the Firebase identity endpoint; Meta name/photo APIs are not read by the current implementation.

The server stores the raw game-scoped ID only in server-readable `providerIdentities`. It derives a generation-separated `facebook_<40 hex>` Firebase UID with a dedicated HMAC secret and issues custom claims containing only the provider and account generation. One-use nonce records store creation/expiry/consumption and, after consumption, a SHA-256 player-ID hash. New nonce issuance now includes a Firestore timestamp at its exact five-minute numeric acceptance deadline. The committed `facebookIdentityNonces.expiresAt` policy and bounded legacy backfill prepare asynchronous physical cleanup; the exact live field read on 2026-10-01 showed no TTL configuration, so deployment and physical deletion acceptance remain outstanding. Expired, missing, consumed or corrupt nonce records cannot authenticate. Provider identity records remain without TTL. Firestore rules deny all client access to provider identities and nonce records. See [nonce retention evidence](../../facebook/evidence/facebook-nonce-retention-2026-10-01.md).

In-game deletion and Meta's signed deletion callback converge on the same cleanup. The provider record advances its account generation, clears the active UID, and retains the server-only provider scope—including the raw game-scoped player ID and app ID—plus status/generation, creation metadata, a SHA-256 old-UID hash, and deletion metadata. The raw player ID is required to derive a later generation-separated UID; a later explicit fresh start creates that UID and a 300-coin profile. The callback receipt uses an opaque confirmation code and exposes no player identifier. Before in-game deletion, a random browser deletion epoch invalidates other current-build same-origin tabs and an origin-wide Web Lock drains accepted work; after server success, the two exact FBInstant preference/player-state keys are nulled and flushed. The epoch contains no player identifier and remains only as a same-origin coordination generation. Live Meta retention, cross-device SDK propagation, platform deletion behavior, contract roles, age-category availability, and real-device behavior remain production-verification and owner/counsel items.

Facebook social context IDs are never stored raw by game services. The server stores a domain-separated SHA-256 context key, context type, locale, provider-scoped member UIDs, join/active state, host UID, and seven-day logical expiry. Independently authenticated joins establish server-owned known-rival relationships; the client cannot nominate another player. A context-board entry contains the provider-scoped UID, authoritative run ID, adjusted milliseconds, completion time, and the same seven-day expiry, but callable responses project only rank/time/current-player. The committed TTL covers entry documents. The new bounded hourly Facebook scheduler atomically removes expired parents and their score entries, retaining only identity-free metadata within its original 30-day history window. A read-only Functions check on 2026-10-01 confirmed that scheduler is not deployed, so automatic physical cleanup remains a rollout gate. Parent TTL stays absent because it does not cascade to scores. Rollover deletes every old entry and retains identity-free board metadata for 30 days. Account deletion removes the UID and entry from memberships and deletes all remaining entries before an empty board. No Meta name or photo is copied into these records.

Native Facebook tournament creation/sharing sends Meta an official best adjusted time in milliseconds, a localized title and generated identity-free PNG, and a five-field payload containing a versioned kind, locale, official daily ID and UTC start/end timestamps. An improved authoritative run may update the matching native score. The game reads the native tournament/context ID, expiry and payload only in memory to verify presentation scope; it persists no raw native tournament ID and sends no Firebase UID, run ID, answer or reward in this payload. Meta already associates its authenticated player with native participation; this does not make the transfer anonymous to Meta. Meta retention, recipient copies, deletion and hosted device behavior remain unverified. Native data never supplies official ranks or economy authority. See [adapter and browser evidence](../../facebook/evidence/facebook-native-tournaments-2026-10-01.md).

Presence is explicitly opt-in. RTDB stores one random session record per active tab/device with provider target, coarse `online`/`playing`/`racing` state, and server timestamp, plus a server aggregate and opt-in bit. Server-only visibility and reverse-index edges restrict reads to established rivals; either party's block and account deletion revoke them. `onDisconnect` removes crashed connections. When the final connection disappears, aggregation persists an unreadable `offline` status and `presenceOptIn: false`; account deletion removes those records. Session IDs are not Meta IDs and are not exposed through rival reads.

### Reddit Devvit platform data

The Reddit webview does not receive raw Reddit identity or call Firebase directly. The
request-scoped Devvit server compares the current-user profile ID with trusted
`context.userId`, accepts only bounded profile fields and HTTPS avatars from the
approved Reddit CDN allowlist, and signs an operation-specific assertion to Firebase.
Firebase stores the raw Reddit ID and a sanitized profile cache with a 24-hour
logical expiry only in a server-readable provider record. Expired profile fields
are suppressed from social responses. A bounded hourly field-removal scheduler is
now prepared locally but is absent from the deployed-function listing; physical
cleanup requires index readiness, deployment and production verification. Refresh
and account deletion already remove the cache. A TTL on that nested field would
delete the identity record itself and must not be used. It derives a generation-separated
`reddit_<40 hex>` UID with a dedicated HMAC secret; browser responses contain opaque
session state, not the raw ID, name, or avatar.

Reddit preference/player storage is asynchronous and authoritative in Firebase. Local
browser state remains low-integrity. In-game deletion advances the provider account
generation before cleanup and deletes the cached profile; an explicit fresh start
creates the next generation with 300 coins. Stale generation retries cannot delete the
new account. Devvit Redis is not used as canonical global profile, balance, receipt, or
entitlement storage. The inactive-by-default Reddit commerce path stores server-only
Gold order replay receipts, refund receipts, and hidden coin debt in Firebase; it is
not exposed until Reddit approves the products and the deployment explicitly enables
commerce. Checkout metadata contains a stable 256-bit HMAC account tag derived by the
Devvit server from app scope and Reddit user ID. It contains neither the raw ID nor a
Firebase UID and is used to manually isolate bounded order-history recovery before each
order re-enters the idempotent Firebase ledger. Notifications are not complete and must
not be described as active processing.

The prepared Devvit server also retains one installation-local canonical game-post
reference in Redis. Its value is a `t3_` post ID or a constant pending-creation marker;
it contains no player profile, identity or economic data. Pending creation has no
automatic expiry because an uncertain submission must not authorize a duplicate.
An unavailable retained post does not trigger replacement. Installation retention
and operator recovery still need hosted verification; see the
[canonical post runbook](../../reddit/reddit-games-operations.md#canonical-game-post-creation).

The inactive-by-default Reddit referral ledger stores only hashed seven-day tokens,
provider-scoped Firebase UIDs in unresolved bindings/daily caps, and idempotent settlement
receipts. Referral provenance stores locale, sandbox/production environment, and a
domain-separated hash of the signed Reddit post ID—not the raw post ID. Account deletion removes live tokens, bindings, and caps and replaces linked
settlements with identity-free replay tombstones. Reddit post-entry attribution is not
active until a real Devvit post payload is captured and its server trust contract passes.

### 2. Riddle Quest Firebase/GCP data

#### Identity, authentication, and profile

- Each Jest session exchanges a recent signed platform assertion for a Firebase custom token. A server-only, hashed `providerIdentities` record binds the platform player to the current account generation. Generation 1 preserves the legacy Firebase UID; a completed reset creates a different UID for the next generation. Claims contain `jestPlayerId`, registration state and `jestAccountGeneration` ([identity mapping](../../../platforms/web/jest/server/jestIdentity.ts), [exchange endpoint](../../../platforms/web/jest/server/jestEndpoints.ts)).
- Game-account deletion writes `jestAccountDeletionTombstones/{uid}` before cleanup. The record retains the pseudonymous UID, schema version, blocked status, deletion time and completion proof. Jest records additionally retain a hashed provider binding and temporarily hold a cleanup lease. Every current authenticated non-delete callable rejects that old UID; signed commerce/referral transactions also bind to the requested current account generation ([deletion guard](../../../platforms/web/jest/server/jestAccountDeletion.ts), [lifecycle](../../../platforms/web/jest/server/jestAccountLifecycle.ts), [guarded endpoints](../../../platforms/web/jest/server/jestEndpoints.ts)).
- Successful deletion removes the Firebase Auth user, including a previously retained disabled Jest record. The permanent Firestore guard rejects old credentials even if an already-issued custom token is redeemed after deletion and recreates an orphan Auth identity. The game no longer intentionally retains or creates disabled Auth sentinels. Fresh start requires completed cleanup, no live cleanup lease, and the exact deleted UID; it creates a separate account generation ([server cleanup](../../../firebase-functions/src/profile/accountDeletion/deleteAccountData.ts), [post-mint and fresh-start checks](../../../platforms/web/jest/server/jestEndpoints.ts)).
- The deletion callable verifies that trusted `jestPlayerId` and `jestAccountGeneration` claims derive the authenticated UID; missing generation means legacy generation 1. Signed deletion retries carry the exact deleted UID. Legacy retries without a UID can select the initial generation, a pending generation or the last-deleted generation, never an active replacement. The initial-generation fallback recovers a local deletion marker saved before its original server request began. Completed retries skip all data sweeps and may return the active replacement UID so clients preserve its provider-side state ([callable](../../../firebase-functions/src/profile/accountDeletion/deleteAccountCallable.ts), [retry lifecycle](../../../platforms/web/jest/server/jestAccountLifecycle.ts)).
- Every authenticated Firebase callable, regardless of UID format or custom claims, transactionally verifies that the deletion guard is absent and creates an `activeOperations` child lease before running. The deletion callable alone skips its own lease. A lease stores only `expiresAt`, which is an expected callable deadline plus a 30-second diagnostic margin, and is normally deleted immediately afterward. That timestamp is not treated as proof that a timed-out Cloud Run execution stopped: deletion writes the permanent guard first and returns a retryable result while *any* lease remains, including one past its deadline or malformed. An orphan lease requires explicit operator reconciliation only after proving the old execution/revision can no longer write ([callable wrapper](../../../firebase-functions/src/shared/sentryHandlers.ts), [lease protocol](../../../platforms/web/jest/server/jestAccountDeletion.ts), [callable timeout](../../../firebase-functions/src/shared/callableSecurity.ts)).
- A new Firestore `users/{uid}` profile receives the UID, a **synthetic** `${uid}@players.jest.invalid` address (not a player email), a Jest-ID-derived default username, coin/entitlement flags, timestamps, preferred language, statistics, progress, and achievements ([Jest user creation](../../../platforms/web/jest/server/jestUser.ts#L5-L23)).
- The supported user schema also includes username/display name, optional avatar URL, language, currency, registration/login/daily dates and keys, detailed play statistics, progression, achievements, purchase flag, and legacy/unused notification fields ([user schema](../../../src/platform/contracts/firestoreSchemas.ts#L89-L137)).
- Usernames are normalized and reserved in server-only `usernameReservations`, which stores the Firebase UID, normalized and display username, reservation hash, and update time ([reservation code](../../../firebase-functions/src/profile/usernameReservations.ts#L6-L64)).
- Firebase Auth persistence is not explicitly configured; the client calls `getAuth` and signs in with a custom token. The effective browser persistence, token lifetime, and provider-side auth logs must be verified against the deployed Firebase configuration ([Firebase client](../../../src/platform/firebase/browserClient.ts#L103-L108)).

Firestore rules let an authenticated player read only their own `users/{uid}` document; writes are server-only. Direct leaderboard reads and writes are denied; the authenticated leaderboard callable returns only canonical rows whose document ID, embedded user ID, optional subject ID, and live `users/{uid}` backing agree. Authoritative gameplay, race, analytics, receipt, and content records are also server-only ([Firestore rules](../../../firebase-functions/firestore.rules#L20-L35), [leaderboard rule](../../../firebase-functions/firestore.rules#L123-L130), [callable filter](../../../firebase-functions/src/gameplay/leaderboard.ts), [server-only rules](../../../firebase-functions/firestore.rules#L132-L183)).

#### Authoritative single-player gameplay

- Private `users/{uid}/singlePlayerSessions` records contain mode, riddle/content/completion IDs, locale, the canonical answer, attempts, last submitted guess and result, continue/hint/skip state, hashed request inputs and replay results, terminal state, and timestamps ([session type](../../../firebase-functions/src/gameplay/sessions/singlePlayerSessionTypes.ts#L31-L75), [write path](../../../firebase-functions/src/gameplay/sessions/singlePlayerSession.ts#L42-L58)).
- Session tokens and content keys are hashed for Firestore document IDs. Sessions and their binding records receive one fixed expiry 30 days after issue; server reads reject expired state even before asynchronous TTL deletion ([session issue](../../../firebase-functions/src/gameplay/sessions/singlePlayerSession.ts#L69-L143), [expiry enforcement](../../../firebase-functions/src/gameplay/sessions/singlePlayerSessionExpiry.ts#L5-L30)).
- `gameCompletionReceipts` link the Firebase UID, mode, completion key, outcome/reward response, and timestamp to replay-safe progression. Loss receipts expire after 45 days. Correct-completion receipts have no TTL while the account exists, because they guard permanent progression/reward replay ([completion receipt](../../../firebase-functions/src/gameplay/sessions/completeGameLogic.ts#L173-L215), [TTL constant](../../../firebase-functions/src/gameplay/sessions/completeGameLogic.ts#L64)). Account deletion explicitly removes both kinds.
- The user profile accumulates coins, progression, win/guess/streak/score statistics, daily dates/keys, and achievements ([completion update](../../../firebase-functions/src/gameplay/sessions/completeGameLogic.ts#L283-L390)).

#### Multiplayer and data visible to other players

- Race runs store the owner's Firebase UID, challenge/rivalry IDs, locale/category, answer-bearing riddle snapshots, guesses-used/hints/revealed letters, clocks/penalties, ghost events, results, and optionally an opponent display-name/avatar/timing snapshot. New opponent snapshots also carry a server-only `subjectUserId`; it is never included in the response. A stored legacy opponent name/avatar without that subject link is projected only as the generic “Riddle Quest player” with no avatar ([race record and projection](../../../firebase-functions/src/race/runs/raceEngine.ts)). Runs, decks, challenges, attempts, start requests, and nested request receipts are configured with a seven-day expiry ([race TTL](../../../src/races/contracts/raceSchemas.ts#L17-L20), [race writes](../../../firebase-functions/src/race/raceService.ts), [committed TTL policies](../../../firebase-functions/firestore.indexes.json)).
- New identity-bearing race mutation receipts store only a generic opponent label and no avatar at rest. Their expiry is capped to the parent run's persisted expiry. Cached replay first requires that live parent and verifies its owner; it then hydrates only the parent's current linked, privacy-safe opponent projection. A missing parent returns `not-found`, and a parent whose subject link was removed keeps the generic projection, so an orphaned or post-deletion receipt cannot replay a stored name/avatar ([receipt minimization](../../../firebase-functions/src/race/privacy/raceReceiptPrivacy.ts), [transactional replay](../../../firebase-functions/src/race/raceService.ts)).
- A published challenge exposes its creator's display name, avatar URL, category, time to beat, rules and expiry to another authenticated, race-enabled player who has the challenge ID ([preview schema](../../../src/races/contracts/raceSchemas.ts#L304-L324), [authenticated callable](../../../firebase-functions/src/race/api/raceCallables.ts#L161-L167)). The server record also contains creator UID, riddle IDs, timing/penalties and ghost events ([challenge record](../../../firebase-functions/src/race/raceSetupService.ts#L29-L73)).
- A race inbox entry is stored under the challenge creator's user document and contains the challenger's display name, optional avatar URL, category, result, timing delta, read state, timestamp, seven-day `expiresAt`, and `opponentUserId`. The provider-neutral Firebase UID is returned only for a still-linked known rival so the owner can invoke server-authorized block/report actions; it is not a raw Jest or Meta player ID. The expiry is omitted. Deleted or unlinked subjects receive the generic name/no-avatar projection and no target UID ([inbox write](../../../firebase-functions/src/race/raceService.ts), [public projection](../../../firebase-functions/src/race/raceReadService.ts), [inbox schema](../../../src/races/contracts/raceSchemas.ts), [TTL/index policy](../../../firebase-functions/firestore.indexes.json)).
- Blocks are stored under the reporting user's `blockedRivals` subcollection after a transactional known-rival check. Categorized reports contain reporter/target Firebase UIDs, one fixed category, status, and timestamp in the server-only `socialModerationQueue`; no free-form text, platform name, or photo is accepted. Report IDs are request-idempotent and each reporter is capped at five unique reports per UTC day.
- Accepting a challenge re-reads the challenge and its creator's permanent deletion guard in the same Firestore transaction that creates the challenger run. A creator deletion that races the earlier preview therefore prevents a new identity snapshot from committing ([transactional start](../../../firebase-functions/src/race/raceService.ts)).
- The permanent deletion guard remains the authority after a run starts. Mutation, cached replay, resume, duplicate-start, and publish paths transactionally check a linked opponent and physically replace a tombstoned or unlinked identity with the generic name and no avatar/subject link before writing. A finishing challenger separately checks the challenge creator's guard in the same transaction and skips the inbox and creator-achievement writes when it exists. Challenge previews check the creator guard, and inbox pages batch-check their bounded set of opponent IDs; both return and persist the generic projection for a tombstoned subject ([opponent privacy resolver](../../../firebase-functions/src/race/privacy/raceOpponentPrivacy.ts), [canonical settlement](../../../firebase-functions/src/race/settlement/raceSettlement.ts) and [idempotent delivery](../../../firebase-functions/src/race/settlement/raceSettlementDelivery.ts), [read projections](../../../firebase-functions/src/race/raceReadService.ts)).
- Leaderboard rows expose the stable Firebase UID, username, optional avatar URL, level, XP, total wins, best streak, and update time through an authenticated callable; responses are capped at 100 rows. New rows use the Firebase UID as both document ID and server-only `subjectUserId`. The callable suppresses orphaned and noncanonical historical rows and verifies a live profile with bounded Admin reads; it never treats a matching name or avatar as proof of ownership. Direct client reads are denied ([row projection and live-user filter](../../../firebase-functions/src/gameplay/leaderboard.ts), [Firestore rule](../../../firebase-functions/firestore.rules#L123-L130), [Firebase client response](../../../src/platform/firebase/browserClient.ts#L157-L172)).
- Race analytics stores an allowlisted event name/parameters plus a stable salted SHA-256 cohort hash of the Firebase UID. It omits the direct UID and expires after 30 days ([event fields](../../../src/races/contracts/raceAnalyticsSchemas.ts#L6-L23), [storage](../../../firebase-functions/src/race/access/raceRollout.ts#L33-L38), [write/expiry](../../../firebase-functions/src/race/access/raceRollout.ts#L72-L95)).

#### Avatars

- A registered Jest player's SDK avatar URL fills an empty game profile avatar automatically. The callable checks the matching Jest identity, requires an HTTPS URL, and preserves an avatar already chosen by the player ([client](../../../platforms/web/jest/src/JestPlayApp.tsx), [server](../../../platforms/web/jest/server/profile/syncJestAvatar.ts)). This stores a provider-hosted URL, not a copy of its image bytes. Account deletion removes the saved URL from the game profile and leaderboard, but cannot recall images already shown in another player's cached race view.
- Registered Jest players can select a JPEG, PNG, or WebP up to 5 MiB. The browser center-crops it to 256 by 256 pixels and re-encodes those pixels as a WebP of at most 512 KiB, so the original file is not uploaded ([browser preparation](../../../src/accounts/browser/avatarImage.ts#L1-L68)). The server accepts at most 512 KiB and validates the declared type and file signature ([decoder](../../../firebase-functions/src/profile/avatarUpload.ts#L1-L29)).
- The object is stored at `avatars/{uid}/profile` with a download token and `Cache-Control: public,max-age=86400`; its tokenized download URL is saved to the profile and leaderboard ([upload](../../../firebase-functions/src/profile/updateAvatar.ts#L14-L49)). Anyone who obtains the tokenized URL can fetch the image, including through leaderboard/race display. Storage SDK reads are otherwise denied by rule ([Storage rules](../../../firebase-functions/storage.rules#L1-L10)). Deletion removes the object, but the code cannot recall copies already shared and does not invalidate already-cached content before its configured 24-hour cache lifetime.

#### Purchases, subscriptions, and referrals

- Facebook commerce currently has a server-internal verified-input ledger but deliberately no externally reachable grant/refund endpoint until Meta's real signed purchase and raw webhook fixtures are captured. `facebookCommerceReceipts` stores provider, Firebase UID, product/kind, purpose-scoped payment/token hashes, gross/net coin accounting, purchase time, and refund time. `facebookCommerceAccounts` stores hidden coin debt and the remove-interstitial entitlement; `facebookCommerceRefunds` stores the linked hashed purchase receipt and refund accounting. Firestore clients cannot read or write any of these collections. Account deletion removes the live account record and replaces UID-linked receipt/refund records with identity-free replay tombstones. A later verified refund updates/creates only identity-free replay tombstones; it cannot recreate the user, balance, debt, or entitlement ([ledger](../../../platforms/web/facebook/server/facebookCommerceLedger.ts), [rules](../../../firebase-functions/firestore.rules)).
- Facebook referral entry data contributes only a 43-character opaque token. The server stores its hash with inviter UID and seven-day issue/expiry times, then stores one immutable invitee/inviter binding after authenticated App Check. New tokens carry an exact Firestore TTL timestamp, and bindings retain the issuance window so matching retries survive temporary-token cleanup. A bounded atomic legacy backfill is prepared; neither backfill nor the committed TTL policy has been deployed/accepted in the 2026-10-01 read-only check. Daily cap records contain inviter UID, UTC day, and count. First-win settlement receipts store both UIDs, two reward amounts, and settlement time while the account exists. Deletion removes active tokens/bindings/caps and anonymizes settlement receipts to reward/time replay evidence ([referral authority](../../../platforms/web/facebook/server/facebookReferrals.ts), [entry parser](../../../platforms/web/facebook/src/referrals.ts)).
- Signed purchases update the user's coins, purchase flag, login time, and first-purchase achievement. New `jestPurchaseGrants` records store a SHA-256 purchase-token hash as both document ID and field, SKU, coin value, timestamp, and replay-protection flag; no raw token or direct UID is written in the current format ([purchase grant](../../../platforms/web/jest/server/jestEndpoints.ts#L233-L318), [hashing](../../../platforms/web/jest/server/jestPurchaseReceipts.ts#L1-L23)).
- Signed subscription state writes `hasActiveSubscription`, active SKU values, verification timestamp, and login time to the user profile ([subscription sync](../../../platforms/web/jest/server/jestEndpoints.ts#L325-L365)). Production UI exposure and provider billing records are Jest concerns; this is the game's entitlement copy.
- Referral verification receives Jest-signed inviter/invitee platform IDs, registration timestamps, and eligible references. It deduplicates conversions by invitee; `joinedAt` is validated but not persisted by current writes ([conversion parser](../../../platforms/web/jest/server/jestReferralReceipts.ts#L17-L73)).
- A latest `jestReferralVerifications` checkpoint stores reference labels, conversion count, and verification time under a document ID derived from the inviter's player ID. Each granted pair creates a permanent `jestReferralRewards` replay receipt under a deterministic SHA-256 ID derived from both platform IDs; the current receipt body contains only reference, reward amounts, timestamp, and replay flag ([referral grant](../../../platforms/web/jest/server/jestEndpoints.ts#L368-L461), [receipt IDs](../../../platforms/web/jest/server/jestReferralReceipts.ts#L46-L55)). Although raw IDs are absent from the current receipt body, the deterministic pair-derived document ID remains a pseudonymous linkability artifact and is retained for replay protection.
- Referral reconciliation can create a synthetic Riddle Quest Firestore user profile and award coins for a referred player before that player starts their own Firebase session ([referred-user creation](../../../platforms/web/jest/server/jestEndpoints.ts#L397-L443)). **Owner/counsel decision:** define how an invited non-returning player's game-side record is surfaced in access/deletion workflows.

#### Request security and operational logs

- Browser-facing Firebase callables require Firebase authentication where the handler checks it and enforce Firebase App Check outside emulators ([callable policy](../../../firebase-functions/src/shared/callableSecurity.ts#L3-L12)). The application does not persist those IP keys. Provider ingress/security logs may have separate retention; production verification is required.
- Firebase/GCP application logs contain Firebase UIDs in several explicit messages, including profile/stat updates, leaderboard operations, avatar failures, and riddle-supply checks ([profile/game logs](../../../firebase-functions/src/gameplay/firestoreService.ts#L35-L57), [leaderboard logs](../../../firebase-functions/src/gameplay/leaderboard.ts#L388-L395), [riddle-supply log](../../../firebase-functions/src/riddles/riddleSupply.ts#L18-L62)). ### 4. Analytics and error telemetry

#### Google Analytics

Jest and Facebook configure their existing web streams, and Android includes native Firebase Analytics. Collection defaults to on when no preference has been saved. Web Settings and native Account/offline menu controls allow players to opt out, and explicit opt-outs persist across reloads or restarts. The [analytics implementation and event catalogue](../observability/google-analytics.md) records current targets, payload bounds, advertising controls and production setup.

Web preferences are target-scoped in local storage. Revocation cancels pending initialization, disconnects collection and removes GA cookies. Events while disabled are discarded. The previous web implementation removed the preference on opt-out, so an absent legacy key cannot distinguish a previous opt-out from a new player. Browser transport replaces page URL/referrer metadata with a fixed origin-only location and empty referrer. Android keeps device-scoped preferences in native app-private storage, disables automatic screen reporting and removes advertising ID/AdServices permissions. Neither transport sends game account IDs, names, entered guesses, answers, purchase tokens or raw error text. When enabled, Google still processes analytics instance identifiers and SDK/transport metadata.

The consent-owned expanded collector also reports foreground session/screen intervals, accepted action counts, bounded content classifications and operation/load durations. Browser performance reports contain numeric timing aggregates without URLs, DOM labels or input text. Only validated campaign codes map to GA acquisition fields; raw referrer/query data, search terms and ad-click identifiers remain excluded. See the [expanded collection and reporting definitions](../observability/google-analytics.md#expanded-collection).

Native Jest and Facebook telemetry remain separate from this consent-controlled GA copy. Reddit, YouTube, GameSnacks and standalone candidate/handoff builds do not gain an external analytics destination. Source checks require consent gates and forbid eager tags in entry documents; target artifact guards retain their SDK/network exclusions. Console retention, linked products, enhanced measurement and access settings need review against the deployed property. Local builds do not verify ingestion or delete historical provider records.

#### Jest analytics

Sanitized funnel parameters and the shared game event stream are sent to Jest through `captureEvent` after successful startup. Attributed funnel events have one native delivery path to avoid duplicates. Native delivery stops when the startup session retires or its deletion gate closes. That platform copy is not governed by the game-configured GA property. Jest retention, access, export, deletion, and consent treatment are unknown in this repository.

#### Facebook analytics

After authenticated startup and a successful configuration read for the configured 13+ audience, the Facebook target sends the shared game event stream and `session_started` through Meta's advertised `logEvent` API. Properties become bounded strings, purchase item dimensions are flattened, and numeric values also use `valueToSum`. The native sink stops on session retirement or account deletion. Unsupported hosts skip collection. A separate Google Analytics web copy defaults to on after the same startup gates and respects the player's saved opt-out. Meta's provider metadata, retention, access, export, deletion, and consent treatment are outside this repository.

#### Sentry

- Browser Sentry starts only for a remote production build with an HTTPS DSN. It captures uncaught failures, unhandled rejections, and explicitly reported caught exceptions at a 100-percent error sample rate. It sets `sendDefaultPii: false`, samples zero performance traces, does not capture console warnings/errors as standalone events, and removes the default breadcrumb, browser-session, conversation, culture, and HTTP-context integrations ([browser setup](../../../src/observability/sentry.ts)).
- Browser redaction removes values under sensitive key names, bearer/JWT/image payloads, URL queries/fragments, and free-form message fields while retaining stack frames and bounded structured diagnostics. Its final event boundary also drops ambient SDK `request`, `user`, `contexts`, and breadcrumb fields rather than relying only on `sendDefaultPii` ([browser redaction](../../../src/observability/sentryPrivacy.ts)).
- Function Sentry is enabled when `SENTRY_DSN` is configured, uses `sendDefaultPii: false`, captures errors at 100 percent, samples zero performance traces, applies analogous key/message, credential, image, and URL query/fragment redaction, and removes the same ambient request/user/context/breadcrumb fields before delivery ([function setup](../../../firebase-functions/src/shared/sentry.ts)).
- Sentry organization/project region, retention, access roster, alert integrations, and deletion/export behavior are not in the repository. A production envelope review is also required to confirm the final SDK-generated metadata after redaction.

### 5. OpenAI content generation

OpenAI is used by backend jobs to generate and independently review riddle content, not to answer a player request. The generation request contains instructions, locale, and up to 80 existing/generated answer words to exclude; review contains the candidate question/answer and locale. Both requests set `store: false` ([generation request](../../../firebase-functions/src/riddles/openaiService.ts#L248-L290), [review request](../../../firebase-functions/src/riddles/openaiService.ts#L190-L217)). No Firebase UID, Jest player ID, profile, player guess, or player message is added to these requests by the current code.

OpenAI account/project access, provider abuse-monitoring retention, data location, and contract settings are not in the repository. Generated riddles are stored in Firestore as shared game content, not as player records ([generation storage](../../../firebase-functions/src/riddles/riddleGeneration.ts#L23-L101)).

## Account deletion reality

The in-game Profile flow calls an authenticated Firebase Function and, after success, signs out Firebase ([client service](../../../src/platform/firebase/browserHostServices.ts#L168-L181), [callable](../../../firebase-functions/src/profile/accountDeletion/deleteAccountCallable.ts#L8-L23)). The server currently:

1. writes the permanent pseudonymous Firebase-UID deletion guard before cleanup and refuses to sweep while any authenticated callable lease remains; Jest also serializes deletion sweeps with an owner-specific cleanup lease;
2. deletes subject-linked race inbox snapshots in other users' trees; first anonymizes the parent opponent projection, then nested legacy replay receipts, then the subject lookup in other users' runs; and uses still-present challenge/run/attempt links for best-effort legacy cleanup before those owned lookup records disappear;
3. deletes directly owned documents from listed legacy analytics/notification/progress collections, race runs and their nested replay receipts, challenges, start requests, attempts, race analytics, tutorial state, and completion receipts; then performs an indexed collection-group sweep by receipt owner UID to catch orphaned receipt subcollections whose parent run was already TTL-deleted;
4. converts legacy UID-linked Jest purchase grants plus Facebook and Reddit commerce receipts/refunds to permanent hashed replay tombstones, and deletes the live provider debt/entitlement accounts;
5. deletes the latest Jest referral-verification checkpoint, removes explicit platform IDs from legacy Jest referral receipts, deletes active Facebook referral tokens/bindings/caps, and anonymizes Facebook settlement receipts;
6. deletes the username reservation, canonical leaderboard row, and subject-linked noncanonical leaderboard rows;
7. recursively deletes `users/{uid}` and its subcollections;
8. deletes `avatars/{uid}/` and `exports/{uid}/` Storage prefixes; and
9. deletes the Firebase Auth user and records cleanup completion. The old UID guard remains permanent; only after the deletion sweep releases its lease may an explicit fresh-start exchange create a new generation ([server implementation](../../../firebase-functions/src/profile/accountDeletion/deleteAccountData.ts), [Jest lifecycle](../../../platforms/web/jest/server/jestAccountLifecycle.ts)).

Before the server request starts, the client persists the deleted UID and a verified `authoritative-deletion-pending` marker, then closes current-build same-origin operations and drains in-flight work through a shared Web Lock. An ambiguous response remains retryable using a fresh signed Jest assertion and the original UID. Confirmed deletion advances to client cleanup: app notification identifiers and SDK state are cleared, Firebase signs out, browser storage is cleared, and the old runtime is discarded. Fresh start then explicitly exchanges the completed deleted UID for a new generation with server defaults. If a newer generation already exists, retry reports its UID so cleanup can preserve its shared provider state. Cleanup/retry failures cannot produce false success ([cleanup](../../../platforms/web/jest/src/accountDeletionCleanup.ts), [backend client](../../../platforms/web/jest/src/backend.ts), [lifecycle](../../../platforms/web/jest/server/jestAccountLifecycle.ts)).

The permanent server guard applies across devices, origins and client versions to the deleted Firebase UID. A replacement UID starts a distinct account generation. Client-side coordination remains origin- and version-scoped; it cannot drain old builds or another device. The repository cannot establish whether SDK key deletion or notification unscheduling propagates across every Jest provider store. Those provider behaviors and historical mixed-version surfaces require separate verification.

The current deletion operation does **not** establish all-data erasure:

- It does not delete the separate Jest player identity/profile, Jest analytics, platform purchase/subscription records, referral shares, or recipient copies.
- It cannot retract already delivered notifications or delete Jest's platform-side notification history. Pending current and legacy D1-D7 engagement and race reminders are explicitly unscheduled.
- It does not target historical Google Analytics records, Sentry, Firebase/GCP logs, reCAPTCHA/App Check records, provider backups, or support email. Analytics-enabled Jest, Facebook and Android builds can create GA records separately from the game account.
- The permanent pseudonymous deletion guard, provider-generation binding and purchase/referral/Premium replay records remain as described in the retention table.
- Facebook deletion also retains the server-only provider identity mapping, including the raw game-scoped Meta player ID and app ID, while clearing the active Firebase UID. Existing identity nonce rows are not part of account cleanup.
- New cross-user race parent snapshots are deleted or anonymized through their server-only subject UID, while new identity-bearing mutation receipts never store the copied name/avatar. Legacy snapshots with a surviving challenge/run/attempt link receive the same cleanup, including nested receipt minimization before the link is removed. A legacy parent whose links already expired cannot be attributed to one subject, so current responses suppress its stored identity; the operator migration anonymizes all existing-parent receipts and deletes parentless receipts at rest. Production must not claim the at-rest migration completed without its recorded aggregate result.
- Orphaned/noncanonical legacy leaderboard rows are not exposed by the callable or direct Firestore access. Production must not claim they were purged at rest until the bounded leaderboard migration has a reviewed aggregate result.
- A cached avatar or image already included in a share cannot be recalled by deleting the Storage object.
- Firestore rules still name legacy `userClassicProgress`, `userDailyChallengeAttempts`, and `tutorialProgress` paths, but no active writer was found in the current tree. The deletion routine now idempotently removes matching progress records and the direct tutorial document so historical data in those documented shapes is covered ([legacy rule paths](../../../firebase-functions/firestore.rules#L62-L97), [deletion inventory](../../../firebase-functions/src/profile/accountDeletion/deleteAccountData.ts)). **Production verification required:** inspect whether historical deployments used any different field or document shape.
- The separate Jest platform identity remains. A fresh Riddle Quest game account can be created under a new generation only after the prior generation finishes deletion; this does not erase platform analytics, shares, purchases, recipient copies or records on other devices.
- The permanent tombstone and callable-lease invariant now apply to every authenticated Firebase UID, including historical non-deterministic identities. Jest adds generation-specific cleanup leases and fresh-start checks. Before release, still run an exact-production aggregate audit across Firebase Auth and every UID-bearing game collection, reconcile or retire identities outside the current deterministic Jest pattern, and verify no historical HTTP endpoint or identity issuer that bypasses the current callable wrapper remains deployed. This audit is needed to find legacy data shapes and retired surfaces, not to make current authenticated callables honor the guard.

Counsel-facing copy must distinguish “delete my Riddle Quest game data” from deleting the Jest platform account and must accurately disclose the exceptions that the owner chooses to retain or remediate.
