# Jest queued player state and startup continuity — 2026-10-03

The Jest player-state hook now replaces waiting complete client projections with the newest accepted projection. It preserves independently updated fields, leaves an already entered SDK snapshot fixed, and creates one queue node and failure report per waiting group. A ready write starts immediately; there is no debounce timer. SDK flush acknowledgement remains the durability boundary.

Each queued player-state or preference operation checks the accepting session generation and target player ID after the existing account-deletion gate acquires its shared lock. Disable and enable retire earlier queued callbacks. An identity change without an enable callback also discards another player's cached fields. Already entered provider promises still drain. An older drain cannot clear a subsequently enabled session.

Startup supplies the new target player ID explicitly before committing its React session. For the same player, reconciliation retains a newer accepted client checkpoint while keeping the incoming hydrated profile. A different issued session or newer provider checkpoint wins. An accepted completion clear supersedes an older stored checkpoint. The real host's riddle/session validation still controls whether a retained checkpoint can resume. Another player's checkpoint is never reconciled into startup.

## Platform scope and remaining work

This change uses the existing Jest adapter and initialization contract. It stores client resume/profile projections, never authoritative purchase grants, identity exchanges or referral rewards. No new SDK signature, console setting, backend configuration, visible text, locale key, ad integration or target dependency was introduced. The Jest HTML5 SDK skill guided lifecycle and storage-boundary checks. Live Jest console/sandbox behavior and production cloud-save latency were not exercised.

The broader improvement goal remains active. Failed-save recovery without subsequent input, player-facing storage failure delivery and remaining asynchronous gameplay ownership are candidates for further investigation. The SDK write already entered before a session retires cannot be cancelled by the hook; it is drained, while future queued writes are rejected by ownership checks.
