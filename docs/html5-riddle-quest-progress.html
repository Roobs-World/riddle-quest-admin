Architecture and acceptance

  • Parity is the primary product requirement. The React game must look, feel, sound and work identically to the former React Native Android app at equivalent viewport sizes.
  • React Native components may be reimplemented with DOM, CSS, Canvas, WebGL and Web Audio, but their visible design, motion, timing, feedback, rules, content and player flows must be preserved.
  • Jest may replace only platform-owned behavior: player identity/registration, loading overlay, payments, notifications, entry payloads, referrals, social profile/avatar and screenshot/share integration.
  • Removing React Native, Expo, Android or iOS code is not evidence of parity. Native retirement is accepted only after every parity row below has code, automated coverage and side-by-side visual/audio evidence.
  • Jest player ID maps to deterministic Firebase UID; registration preserves the same record.
  • Only locale, mute, accessibility, and onboarding preferences may use client-writable Jest data.
  • Purchases and referrals are granted only after server-side HS256 verification and idempotent Firestore recording.
  • completePurchase follows durable grant; incomplete purchases reconcile on every startup.
  • Playable means the initial authoritative profile and riddle are present and input is enabled before markGameLoaded().
  • React/Jest is the only shipped client. The former native source in Git history is the behavioral and visual reference until the parity acceptance suite is complete.

Non-negotiable React conversion contract

The source of truth is the last complete React Native Android implementation in Git history. A feature is not complete merely because a simplified web substitute exists. Every screen, rule, animation, sound, tooltip, state transition, Firebase interaction and accessibility behavior must be inventoried and either reproduced in React or explicitly documented as a Jest-owned replacement.

Execution sequence and release gates

  1. Gate 0 — preserve and inventory the reference. Treat the former React Native Android app in Git history as the product specification. Inventory every screen, component, asset, sound, animation, rule, state transition, tooltip, localized string and backend contract before accepting any deletion.
  2. Gate 1 — reproduce the complete game in React. Port the solar system, game board, custom keyboard, profile, achievements, ranks, statistics, tooltips, onboarding, shops, settings, leaderboards, modal sequences, rewards, music and sound cues with the same appearance, timing, feedback and rules.
  3. Gate 2 — preserve authoritative behavior and data. Match the Android game rules exactly, including five initial guesses, one 100-coin continuation guess, hints, skips, rewards, XP, ranks, streaks, achievements, progression, session restoration and all localized Firebase riddles.
  4. Gate 3 — substitute Jest only at the platform boundary. Use Jest for player identity, registration, loading, payments, notifications, entry payloads, referrals and supported social/share services. Jest does not replace the game's UI, rules, content, progression or Firebase authority.
  5. Gate 4 — optimize without changing the experience. Meet the game-only artifact and startup budgets with compression, code splitting and post-playable loading. Required visuals, textures, sounds, translations and behaviors may not be deleted to obtain a smaller build.
  6. Gate 5 — close the Jest retention, acquisition and monetization loops. Complete Daily Cosmic Riddle notifications, friend challenges and referrals, and the signed catalog purchase flow with authoritative grants and interruption recovery.
  7. Gate 6 — qualification. Run unit/contract tests, browser automation, real-device mobile and 10+ minute lower-end soaks, visual/audio golden comparisons against the Android reference, hosted emulator, registered/guest sandbox, notification, referral and payment matrices.
  8. Gate 7 — submission and Games Fund evidence. Upload the release candidate without publishing; run and record the Simulator self-review; attach measurements, screenshots, event IDs and funnel definitions; submit for platform review only when every basic gate is green, then package the same evidence plus retention/acquisition/monetization loop results for the Games Fund application.

Release rule: "implemented" is not "accepted." A row becomes done only when its code, automated verification, uploaded-build sandbox evidence, and any required Developer Console configuration are all present. Any launch must-have failure blocks submission; Games Fund loop failures may not block basic publication but do block the Games Fund readiness claim.
