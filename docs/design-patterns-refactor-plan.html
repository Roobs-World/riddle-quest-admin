For agents and contributors

How to use this tracker

  1. Read this file before starting refactor work: docs/design-patterns-refactor-plan.html
  2. Do all refactor work on the long-lived branch refactor/design-patterns (create from main if it does not exist). Do not commit refactor changes directly to main.
  3. For each PR in the checklist, branch from refactor/design-patterns using refactor/design-patterns/pr-NN-short-name, then open a PR into refactor/design-patterns (not main) until the epic is complete.
  4. If the tracker is ever reopened, start from the first phase that shows a regression or missing evidence.
  5. Follow architecture rules: domain in packages/core/, thin UI, ports/adapters in src/services/.
  6. One PR per checklist item when possible; keep useAuth, useModal, useGameLogic APIs stable until noted.
  7. After merging, check the PR box, add evidence in handoff notes, and keep this HTML as the audit trail.
  8. Related docs: architecture.mdc, systemPatterns.md, codebase optimization tracker

Progress is stored in localStorage key qwordly-design-patterns-refactor-v1 (per browser). Agents: paste exported JSON into PR description or memory-bank when handoff is needed.

Goals

  • Apply named design patterns at boundaries where complexity lives today.
  • Use patterns to remove real branching, coupling, or duplication; do not add pattern names where a small function is clearer.
  • Move framework-agnostic logic into packages/core/.
  • Keep UI components thin; shrink orchestration-heavy modules.
  • Document every new exported refactor surface with TSDoc that names the pattern, boundary, invariants, and trade-offs.
  • No big-bang — each PR leaves the app runnable with tests green.
  • Keep refactor work off main until the epic branch is ready to merge.

Pattern selection rubric

A refactor PR should pass this rubric before introducing a new pattern-named class, hook, or folder.

Question Accept when Reject or simplify when
What pressure is the pattern relieving? It removes duplicate branching, isolates framework/vendor code, or makes a state transition explicit. It only renames existing procedural code or adds an indirection with one implementation.
Where does the pattern belong? packages/core for pure domain, src/application for orchestration, src/services for adapters. Domain rules remain inside screens, hooks, contexts, Firebase adapters, or modal components.
How will another developer discover it? Exported APIs include TSDoc with pattern name, boundary, invariants, and example usage. The only explanation is a PR description or a class name like *Manager.
How is behavior protected? Unit tests cover the pattern contract and an integration/hook test protects the old public API. The PR moves code without tests that prove equivalent user-facing behavior.

TSDoc documented refactoring rules

  • Every exported class, hook, function, interface, and command type introduced by this refactor needs a /** ... */ TSDoc block.
  • Use @remarks to name the design pattern and explain why it was chosen; avoid custom tags unless the toolchain is configured for them.
  • Document the boundary: what layer owns the symbol, what dependencies are allowed, and what dependencies are intentionally hidden.
  • Document invariants and failure behavior, especially for auth bootstrapping, guest persistence, modal sequencing, retries, and game completion.
  • For compatibility facades, include @see links to the old hook/provider API and the new implementation.
  • Use @internal for adapters, factories, or compatibility shims that should not become app-wide extension points.
/**
 * Coordinates provider-auth startup as a Template Method pipeline.
 *
 * @remarks
 * Pattern: Template Method + Strategy. The pipeline fixes the auth lifecycle
 * order while injected strategies handle guest, provider, and upgraded-account
 * profile reconciliation.
 *
 * Boundary: application layer. Depends on repositories and ports, not React
 * state setters or screen components.
 *
 * Invariants:
 * - One bootstrap run may own a user id at a time.
 * - Late async results must not overwrite a newer auth session.
 *
 * @see useAuthProviderController
 */

Architecture decision records

Add or update ADRs when a pattern changes ownership boundaries or becomes a convention for future contributors.

ADR When required Must include
Core game engine Before GameEngine becomes the source of truth for local transitions. Server-authoritative boundary, state machine responsibilities, and parity-test expectations.
Auth bootstrap pipeline Before splitting useAuthProviderController into strategies. Lifecycle order, duplicate-event guards, guest upgrade behavior, and stale request cancellation.
Service ports namespace Before removing src/services/interfaces/. Port naming rules, adapter registration, singleton policy, and testing overrides.
Modal command and sequence system Before all modal opens flow through the command bus. Registry ownership, command payload typing, fanfare chain order, and escape hatches.
