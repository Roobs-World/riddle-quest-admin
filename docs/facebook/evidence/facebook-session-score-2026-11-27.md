# Facebook session-score integration — 27 November 2026

This records the session-score adapter implementation. It is not hosted acceptance, upload, review or publication evidence. Root integration, the Facebook build and Meta-hosted verification must be recorded separately.

## Score definition and authority

General Facebook session scores use `RACE_MAX_ADJUSTED_TIME_MS - adjustedTimeMs`. The shared race contract defines the ceiling as 300,000 milliseconds. A completed ten-answer race taking 120,000 adjusted milliseconds therefore produces 180,000 points; a slower 150,000-millisecond run produces 150,000 points. The transformation preserves the authoritative race ordering while presenting higher points for faster completion. Existing server penalties are already included in adjusted time. The score grants no coins, entitlements, standings or rewards.

The adapter accepts only the strict `RecordFacebookTournamentRunResponse` parser and requires the response's `runId` to match the requested run. That authenticated server operation verifies a completed qualifying Race to 10 run; browser timers, local guesses, balance and arbitrary native payloads never nominate the score. A response that refers to an older best run rather than the requested run is skipped. Runs completed before this adapter's account session began are skipped. Recording a receipt only makes the explicit share-score action available; it does not open a native dialog.

Meta requires integer session scores from comparable completed activities and warns that excessive calls are rate limited. The asynchronous method may produce native dialogs and change context before it resolves. The adapter uses the asynchronous method when advertised and callable, otherwise its synchronous alternative; it never calls both for one receipt. [Session-score reference](https://developers.facebook.com/documentation/games/sdk-reference/v8.0#postsessionscoreasync)

## Native tournament isolation

Existing official tournament projections use raw adjusted milliseconds with `LOWER_IS_BETTER`. Reversed session points must never be written into that native leaderboard. The adapter requires advertised, callable `getTournamentAsync`, and normally posts only after the explicit `TOURNAMENT_NOT_FOUND` error proves the current native session is outside a tournament. The separately configured private-points mode below also accepts a verified compatible private tournament. Every other returned tournament, unknown/error response, missing API or an eight-second metadata deadline skips posting. It rechecks the captured context, active account, locale, visible game and caller-owned presentation guard immediately before admission. [Current tournament contract](https://developers.facebook.com/documentation/games/sdk-reference/v8.0#gettournamentasync)

The shared Facebook dialog gate prevents overlap with native invitations, payments, ads or other dialogs. The player clicks a lobby action to publish the score. That action owns an abort signal which retires when the surface unmounts or its locale changes, preventing delayed metadata from opening UI over a new activity. Every admitted native score attempt is followed by reconciliation with the existing context coordinator while the account remains current, including after rejection or when the initiating surface has since closed: a response can be lost after the native context changed. Account retirement invalidates late metadata work and prevents further posts.

## Delivery behavior and wiring

`createFacebookSessionScore` takes the initialized SDK, `isActive`, `canPresent`, `getLocale`, `synchronizeContext`, optional `onContextChange` subscription, optional `privateTournamentsEnabled` (default false), and fixed-operation diagnostics. The entry must instantiate it only for an authenticated, enabled 13+ tournament session. Call `sessionScore.record(runId, response)` after the authoritative record operation succeeds. This synchronous method retains an opportunity and returns immediately. Wrap the game in `FacebookSessionScoreProvider` and mount `FacebookSessionScoreActions` in the Facebook race lobby. Its translated action invokes `publish(surfaceSignal)`. Retire the controller on cleanup and account deletion.

Only a strictly improved score is attempted per native context or compatible private tournament during the controller's lifetime. The same verified result can seed a different competition; an initial private score consumes that receipt for the returned tournament. Native context events refresh the available action, and retirement removes that subscription. The run is marked before SDK invocation because an error can follow a delivered side effect; it is not automatically retried. Duplicate record callbacks cannot create another native action, and a pending publication rejects a second click. Failures are contained and never reject an already-completed game operation. No score or raw SDK payload is included in diagnostics.

## Optional private group tournaments

Private tournaments use the same authoritative integer points formula, from 0 through 300,000. `privateTournamentsEnabled` defaults to false, and the root deployment flag is `VITE_FACEBOOK_PRIVATE_TOURNAMENTS_ENABLED`. Neither SDK advertisement nor a callable method enables this feature without that explicit setting. Creation, chooser, listing, and posting are independently gated against their exact advertised and callable methods. The option must remain false until Meta confirms game allowlisting and the App Dashboard's private settings are verified as higher-is-better numeric scores covering this range. This unit does not establish those prerequisites or change Meta configuration.

The player can explicitly start in their current group or choose a group and start. The translated UI discloses that starting posts a leaderboard and the race score into the group chat. The chooser is awaited with `{minSize: 3}` before creation; a `THREAD` context can already be a Messenger group, so no client member-count minimum is imposed. The host validates the actual group. The original or selected context is captured before waiting for presentation guards or reconciliation, and must still match after metadata discovery. Creation requires a fresh `TOURNAMENT_NOT_FOUND` result in that selected context. The shared dialog gate serializes the entire choose-and-create operation. [Private tournament guide](https://developers.facebook.com/documentation/games/retain/tournaments)

The payload is exactly `{initialScore, data: {kind: "rq-race10-points-v1", locale}}`. Native private creation has no per-call sort-order configuration, title or creation dialog; app-level settings control it, and creation posts to the chat immediately. It may join an existing tournament instead of creating one. After success, only a live `PRIVATE` tournament with a strictly parsed, bounded points envelope, matching locale, valid identifiers and matching current context admits later score updates. Ordinary official tournament envelopes and unknown, malformed, expired or foreign data remain blocked. The initial native creation call can already have submitted its score before returning an existing tournament's metadata; rejecting that returned envelope prevents follow-up submissions but cannot undo the initial native call. This is why verified app-wide private scoring settings remain a release prerequisite. [Private creation reference](https://developers.facebook.com/documentation/games/sdk-reference/v8.0/tournament#createprivateasync)

Private scores use `postSessionScoreAsync` (or the advertised synchronous alternative), never `tournament.shareAsync`: the private share API can reject while still submitting its score. Scoring remains an explicit player action and posts a group leaderboard update. No automatic creation, invitations, chat messages or score posts occur when recording a completed race or refreshing context.

## Uncertain creation and native lifetime

A rejected initial score can leave a created tournament and leaderboard message in the chat while the SDK remains in the original group context. Network and rate-limit outcomes are also treated conservatively. Each selected group is marked before its creation call; this session cannot blindly repeat creation for that group, including after receiving a better race receipt. The UI retains an uncertain-outcome message for the affected context. Read-only recovery inspects the current tournament and, when available, the eligible tournament list; a list entry is never assumed to belong to the attempted group, and recovery never joins it speculatively. The context observed when the native mutation settles is captured before reconciliation. A subsequent external context change prevents recovery from consuming the receipt in an unrelated tournament. [Initial-score validation and error semantics](https://developers.facebook.com/documentation/games/retain/tournaments#initial-score-validation)

The two documented `INVALID_OPERATION` messages for game allowlisting and player rollout disable creation for the account session. They do not enable another API or trigger a retry. Every admitted chooser, score or creation mutation reconciles the native context on success or rejection while its account remains active. A retired surface or changed locale prevents follow-on mutations, while an already-admitted native effect still receives account-owned reconciliation. Pending snapshots clear on account retirement. Diagnostics contain fixed operation names rather than native scores, context identifiers or raw messages.
