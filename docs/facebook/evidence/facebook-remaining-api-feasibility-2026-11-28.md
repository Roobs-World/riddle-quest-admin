## Native Android rewarded-ad investigation

Meta’s Instant-Games-specific Audience Network guide says automatic test mode applies when the game has not passed App Review and the testing account has an **Admin or Developer** role. It does not promise this for every Tester-role account or guarantee successful fill. The guide supplies no separate Android versus desktop exemption. Fresh role/review and placement state should therefore be checked before attributing the recorded phone failures to configuration. [Instant Games testing](https://developers.facebook.com/documentation/audience-network/instant-games#testing)

The linked provider-side alternative is **Monetization Manager → Integration → Testing**. It supports registered test devices, Android advertising IDs and selected ad formats without game code changes. Meta says this mode deliberately produces some no-fill responses. Checking the existing property/device setup is a concrete next read-only action; changing it would be a provider testing action, not a Firebase fix. No missing-device diagnosis or configuration change is claimed here. [Platform testing](https://developers.facebook.com/documentation/audience-network/setting-up/testing/platform)

Do not copy native Android Audience Network `AdSettings.addTestDevice` calls or `TEST_AD_TYPE#placement` strings into the FBInstant game. Those examples configure a separately integrated native Audience Network SDK; they are not documented FBInstant controls. [Native device-testing scope](https://developers.facebook.com/documentation/audience-network/setting-up/test/test-device)

The current [ad adapter](../../../platforms/web/facebook/src/FacebookAdsCapability.ts) records generic `ad_failed` events with format and placement, which does not distinguish the failed native stage. A bounded client-only diagnostic can record the attempted phase and an allowlisted code, including whether failure happened before SDK admission. This is a useful implementation follow-up under the backend freeze, without changing entitlement decisions or rewards. Record fixed categories only; omit provider messages, player IDs, raw objects, signatures and receipts.

Use the exact [SDK v8 error contract](https://developers.facebook.com/documentation/games/sdk-reference/v8.0#adinstance), not a generic service message, to classify an observation. A successful `showAsync` signifies completed viewing; early dismissal rejects. The overview recommends delayed retries for no-fill/frequent loads. The existing v15/v16 phone observations captured neither stage nor SDK code, so inventory shortage, throttling, placement configuration, pre-admission eligibility and transport remain hypotheses. Banner success and historical desktop rewarded success do not identify the current fullscreen failure. [Ad error guidance](https://developers.facebook.com/documentation/games/monetize/in-app-ads/overview#common-errors)

Recommended order: inspect the existing provider test setup; add narrowly scoped stage/code diagnostics if native tooling cannot expose them; make one controlled eligible rewarded attempt; then complete banner and ad lifecycle acceptance on the exact resulting candidate. Keep all six G and eleven C rows unchanged until their actual workflow or prerequisite evidence improves.

## Ad-instance ownership and retries — 28 November follow-up

The current v8 reference defines `ADS_TOO_MANY_INSTANCES` as excess concurrent ad instances and advises using existing instances before creating more. It specifies no numerical cap and documents no public AdInstance disposal, release or reset operation. The documented operations are placement lookup, loading and showing. Meta's older GDC 2019 lifecycle guide mentions three preloaded ads; that historical statement does not establish an exact v8 allocation limit. [Current SDK](https://developers.facebook.com/documentation/games/sdk-reference/v8.0#adinstance), [historical lifecycle guide](https://developers.facebook.com/docs/games/instant-games/guides/lifecycle/)

The current ads overview says a shown instance cannot be reused. Its retry guidance recommends a delay after preload failure. The rewarded example retries a function that **creates a new instance**, after 30 seconds for `ADS_NO_FILL` or 60 seconds for `ADS_FREQUENT_LOAD`. These examples do not guarantee that a failed handle can be loaded again, when its provider allocation is released, or that repeatedly creating replacements immediately is safe. No explicit failed-handle reuse/release contract was found. [IAA overview](https://developers.facebook.com/documentation/games/monetize/in-app-ads/overview#preloading-best-practices), [rewarded example](https://developers.facebook.com/documentation/games/monetize/in-app-ads/rewarded-ads#complete-integration-example)

The inspected client creates a local handle per attempt and drops its reference after load failure or pre-show retirement. Its preparation guard tracks unsettled work, not retained native allocations. Accumulation is therefore a hypothesis to investigate, not an established explanation of the initial mobile failure. The [separate native diagnosis](facebook-android-ad-diagnosis-2026-11-28.md) owns the runtime observations. This contract follow-up claims no fresh-first-attempt result and changes no client or backend behavior.
