# Android parity plan

Tracks [ADR 0008](../common/architecture/adr/0008-android-hosted-parity.md): bringing `platforms/native/android` to the Jest Web Target's product surface with native screens. Completion of a step requires implementation plus recorded verification (unit gates, the adb device suite, and where applicable the Firebase emulators). Owner prerequisites are listed per phase; nothing in this plan authorizes a Play upload.

Scale for context: the hosted browser game is roughly 36,000 lines of host, play, race, commerce, profile and notification code with ~150 browser harnesses. The shared-logic/native-views pattern across shared feature controllers is applied phase by phase so logic moves once and only views are written twice.

## Phase 1 — Account and confirmed solo play

- [x] 1.1 Backend: `provisionAndroidAccount` callable creates the Global Game Account for an authenticated Firebase user whose sign-in provider is `anonymous` (later also `google.com`), idempotently, with the same reserved-username and starting-balance rules as Jest. App Check enforced like every other callable.
- [x] 1.2 Shared: the typed callable surface of `src/platform/firebase/browserClient.ts` (protected-content decoding, region binding) lives in `src/platform/firebase/gameFunctions.ts` as `createGameFunctionsClient`; the browser adapter owns Firebase initialization, auth persistence, and App Check. Android-only callables are bound separately (`createAndroidAccountFunctions`) so web targets keep their exact surface.
- [x] 1.3a Shared: the `HostServices` contract, its Firebase implementation (`createFirebaseHostServices` with injected auth, callables, profile reads and copy), and its helpers (authority delivery, profile and riddle mapping, completion reward parsing) live in their platform, account, gameplay, and progression feature folders; browser modules import them directly. Android can create the same services against its React Native auth.
- [x] 1.3b Shared: the DOM-free hosted play session logic now lives under `src/gameplay/session`: the session reducer and its types, `SavedGame` checkpoints (`GameSessionCheckpoints`), the Provisional Play journal (writer, reader, reconciliation, paid settlement, lease), confirmed-outcome recovery and completion presentation ordering; browser components import the canonical feature implementations directly and keep their own browser adapters (`localStorage`, `window` timers) and React hooks. `HostedPlaySession` itself stays in the portal because it assembles target-owned facts (platform capabilities, presence, referral sharing). Android journals every hosted draft and in-flight guess through the same journal over AsyncStorage (`createAndroidPendingPlayStorage`): a guess that fails in transit is redelivered with its original request id on the next launch, an edited answer cancels the redelivery, a rejected guess is dropped, and a journal left by another question is discarded.
- [x] 1.4 Android: Firebase JS SDK with AsyncStorage auth persistence, anonymous sign-in, account provisioning, and an account screen showing the confirmed balance; emulator configuration (`10.0.2.2`) for local verification. App Check (1.7) is still required before production calls succeed.
- [x] 1.5 Android: hosted-first launch (`AndroidApp`): the device connects on start, lands on a hosted home with server-issued Classic and Daily (`HostedGameScreen` + `useHostedGame`; guesses, hints, continue, skip and completion are server-confirmed and the balance comes from the account document), the Account screen, and Play offline. Copy comes from the shared `src/localization/copy` tables plus a hosted-only table covering every supported locale. The self-contained game is the offline surface, reachable from the connect screen and the home and returning through Play online; the choice is per session (4.1 decides whether it stays). Provisional Play buffering arrived with 1.3b.
- [x] 1.6 Verification: backend unit tests for provisioning; services-group tests; adb suite running against the Firebase emulators with a seeded account.
- Firebase prerequisites verified: Android app registration, public app configuration, App Check exchange endpoints and API enablement. This implementation initializes its native Firebase app at runtime and does not require `google-services.json`. Play Console linkage and a recognized installation remain open under 1.7.
- [x] 1.7 Attestation (code): `issueAndroidAttestationNonce` issues a single-use nonce; the app's `RiddleQuestPlayIntegrity` native module (Play Integrity 1.6.0) binds an integrity token to it; `exchangeAndroidAttestation` decodes the token with the Play Integrity API, requires this package, the issued nonce, a verdict under two minutes old, `PLAY_RECOGNIZED` and `MEETS_DEVICE_INTEGRITY`, then mints an App Check token for `ANDROID_FIREBASE_APP_ID`. The JS SDK uses it through a `CustomProvider` (`src/hosted/appCheck.ts`); emulator builds skip App Check. Firebase Android registration, the matching public `ANDROID_FIREBASE_APP_ID`, the enabled Play Integrity API, the nonce TTL policy and both deployed endpoints are verified. Remaining owner steps: create the Play developer account, link the Cloud project under Play Console → App integrity, and verify attestation from a recognized installation.
