QA STRATEGY

Riddle Quest Exhaustive Android Emulator and Firebase QA Plan

This document defines the testing strategy for validating every meaningful piece of functionality in the Riddle Quest/Qwordly Expo React Native project. The goal is to leave nothing to chance: every page requested for coverage, every registered modal, every gameplay branch, every Firebase write path, every persistence path, and every expected error or edge state must be exercised, evidenced, and logged for both guest users and provider-authenticated users.

Important: Forgot Password, New Password, and Game screen are intentionally excluded as standalone page coverage items per user request. Gameplay functionality is still fully in scope because Firebase progress, wins/losses, hints, skips, coins, stats, and modal flows cannot be verified without exercising gameplay.

Execution Rules

  • Use Android Studio MCP for Android SDK setup, emulator downloads, AVD creation, emulator launch, screenshots, and logs when available.
  • Use Expo MCP for Expo, React Native, EAS, simulator, and React Native DevTools tasks when available.
  • If MCP tools are unavailable, use Android SDK, emulator, ADB, and Expo CLI fallbacks. Record the fallback in this HTML file.
  • Maintain this HTML file continuously. It is the single source of truth for strategy, progress, blockers, defects, skipped items, Firebase snapshots, screenshots, logs, and handoff notes.
  • Save screenshots under emulator-tests/images/{device-name}/ and logs under emulator-tests/logs/{device-name}/.
  • Do not deploy Firebase Functions, change Firestore rules, or edit live production data outside the disposable QA account.
  • Do not mark an item passed without evidence. Evidence means a screenshot, log, Firestore before/after snapshot, UI tree snippet, or a precise written observation in the todo file.
  • Every functional test must be executed for both personas unless the feature is explicitly persona-specific: guest/anonymous user and provider-authenticated user. If a flow only applies to one persona, mark the other persona SKIPPED with the reason.

User Persona Matrix

All coverage must be evaluated against both user models. Do not assume a feature that works for one user type works for the other.

  • Use separate Firebase/local-storage evidence for persona-specific persistence behavior.

Functionality Coverage

The testing strategy must treat the project as a whole product, not only a happy-path game loop. Every item below must be tested, marked with a status, and backed by evidence.

Authentication And Session

  • Cold launch with no authenticated user.
  • Guest/anonymous entry and guest-only local behavior.
  • Disposable non-guest account for live Firebase writes.
  • Email/password login if available.
  • Sign up if reachable.
  • Invalid auth inputs and visible error messages.
  • Social auth buttons render and either work or fail gracefully.
  • Logout returns to unauthenticated flow and clears local state as expected.
  • Upgrade account flow from guest profile path.
  • Guest account deletion from profile details opens confirmation, supports cancel, confirms deletion, signs out, clears local guest state, and returns to the unauthenticated flow.
  • Auth-provider account deletion from profile details opens confirmation, supports cancel, confirms deletion through the deleteAccount callable, signs out, and prevents the deleted provider account from silently restoring stale app data.
  • Account deletion failure path shows the expected error modal and does not force logout or leave the profile modal in a broken loading state.
  • App restart after login restores expected session.
  • Every shared session function is validated for both guest and provider-auth personas, including navigation state, profile state, settings state, logout/delete state, and restart behavior.

Riddle Loading And Mode Selection

  • Daily Challenge available path.
  • Daily Challenge already completed/unavailable fallback to Classic.
  • Classic mode riddle fetch by progress.classicIndex.
  • Riddle initialization/loading spinner behavior.
  • Riddle initialization retry/error behavior if triggerable.
  • Current riddle changes after win, skip, or next level.
  • Mode label renders correctly for Daily/Classic states.

Core Gameplay

  • All gameplay paths below must be tested once as guest and once as provider-authenticated user, with persona-specific persistence expectations.
  • Letter input through on-screen keyboard.
  • Backspace behavior on empty and populated guesses.
  • Tapping guess slots changes active slot correctly.
  • Submit disabled for incomplete guesses.
  • Submit enabled for complete guesses.
  • Incorrect guess feedback with red/yellow/green states.
  • Duplicate-letter feedback where a suitable riddle/guess exists.
  • Correct guess win path.
  • Loss after exhausting attempts.
  • Continue offer after initial attempt limit.
  • Coin continue path.
  • Rewarded-ad continue path if ad is available.
  • Final loss after continue attempts.
  • Next level after win.
  • Skip level from controls.
  • Keyboard color/state preservation across guesses and mode changes.
  • Game state reset between riddles.

Economy, Rewards, And Shop

  • All economy and shop paths must be tested for both guest and provider-authenticated users; record where purchases, ads, or backend writes differ by persona.
  • Coin display reads current balance.
  • Coin animation after rewards and purchases.
  • Hint purchase spends coins and reveals one unrevealed letter.
  • Multiple hints reveal different slots until no hint remains.
  • Insufficient coin behavior for hint, skip, and continue.
  • Skip spends correct mode-specific coin amount.
  • Coin continue spends correct amount.
  • Victory rewards display correct coins and total.
  • Achievement bonus coins display and persist.
  • Coin shop opens from header and insufficient-coin paths.
  • Coin shop product loading, empty, error, watch-video, pay/play, and purchase attempt states.
  • Coin purchase fanfare where triggerable.

Profile, Stats, Achievements, Leaderboard

  • All profile surfaces must be tested for both guest and provider-authenticated users, including upgrade prompts for guests and backend refresh for provider-auth users.
  • Profile modal opens and refreshes latest Firestore-backed player data.
  • Delete Account button is present in profile actions for guest users and auth-provider users.
  • Delete account confirmation text, destructive styling, cancel action, confirm action, loading state, and close/back behavior are correct.
  • Stats modal renders games, wins, streaks, XP, level, and averages correctly.
  • Achievements modal shows locked and unlocked states correctly.
  • Achievement unlock fanfare appears when achievements unlock.
  • Leaderboard opens, loads data, switches tabs, and handles empty/error states.
  • Update username modal opens where reachable, validates input, saves, and reflects the updated name.

Settings, Preferences, And System UI

  • All settings and system UI paths must be tested for both guest and provider-authenticated users.
  • Settings modal opens and closes.
  • Sound toggle updates UI, persists, and controls mute overlay behavior.
  • Haptics toggle updates UI and persists.
  • Language selector changes visible strings or logs unsupported behavior.
  • Help/support email link is invoked or fails gracefully.
  • Credits modal opens from settings.
  • About/Legal modal opens from settings.
  • Back button behavior closes modals and does not corrupt game state.
  • Offline modal appears when connectivity is disabled and clears after reconnection.

Persistence And Recovery

  • Persistence must be verified separately for local guest storage and provider-auth Firestore-backed data.
  • Guest progress persists locally across app restart.
  • Guest progress remains local and does not create backend game-completion writes.
  • Non-guest progress refreshes from Firestore.
  • Settings persist across app restart.
  • In-progress guest session restore works where applicable.
  • Network interruptions do not leave the UI permanently stuck.
  • Loading spinners appear and disappear correctly.
  • Crash-free behavior through all tested flows.

Visual, Accessibility, And Device Fit

  • Visual and accessibility checks must cover both personas where content differs.
  • No clipped text, overlapped UI, unreachable buttons, or off-screen modals.
  • Safe-area behavior is correct on every device profile.
  • Tablet and foldable layouts scale intentionally in portrait.
  • Touch targets are large enough and consistently tappable.
  • Accessibility labels exist for critical controls where exposed in UI tree.
  • Dynamic content does not resize controls unexpectedly.
  • Animations do not block interaction or cause stuck loading states.

Expected Mutation Checks

  • Classic win reward: 15 coins plus achievement bonuses.
  • Daily win reward: 50 coins plus achievement bonuses.
  • Achievement unlock reward: 25 coins each.
  • Hint cost: 50 coins and increments stats.totalHintsUsed.
  • Classic skip cost: 100 coins.
  • Daily skip cost: 150 coins.
  • Coin continue cost: 100 coins.
  • Wins increment games, wins, total wins, guesses, XP, progress, and streak fields as appropriate.
  • Loss increments games and total guesses but not win counters.
  • Leaderboard entry updates for non-anonymous users when applicable.
  • Account deletion removes users/{uid}, leaderboard/{uid}, user-owned purchaseAnalytics and notificationHistory docs, avatar/export storage prefixes, and the Firebase Auth user.
  • Guest account deletion must remove the anonymous Firebase Auth user and local guest data without leaving a restorable guest profile on app restart.
  • Provider-auth account deletion must remove the provider-backed Firebase Auth user and Firestore profile data; a later sign-in with the same provider should create a fresh account/profile rather than reviving deleted progress.

  • Every registered modal has PASS, FAIL, SKIPPED, BLOCKED, or UNREACHABLE status with evidence.

  • Every shared functionality item has separate guest and provider-auth status, or a documented persona-specific skip reason.
  • Every live Firebase write path has before/after snapshots and expected-vs-actual deltas.
  • Guest and auth-provider account deletion are both verified with UI evidence, local-session evidence, and Firebase/Auth cleanup evidence.
  • No issue is left as a vague note; each issue has reproduction steps and evidence.
  • The final QA report references screenshot directories, log paths, Firebase UID, deltas, pass/fail summary, defects, and cleanup.
